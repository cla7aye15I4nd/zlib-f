压缩文件必须交给一个没有见过原文的接收者，仍能恢复出原文。这一要求决定了整个设计：怎样描述重复，怎样把描述变成位，接收者怎样知道这些位的含义，又怎样知道何时结束。我们先造出一套完整的小型编解码器，再看 zlib 中对应的做法。

## 找到更短、又能还原的描述 {#purpose}

假设要把 `ABABABAB` 发送给另一台计算机。在这里使用的字节约定中，A 的数值是 65，十六进制写成 `41`；B 的数值是 66，写成 `42`。整条消息有八个字节：

```text
41 42 41 42 41 42 41 42
```

一个**字节**有八个二进制位，简称“位”，可以表示 0 到 255 的任意整数。十六进制用两位数字写出一个字节，每位数字代表四个二进制位。因此，`41` 表示位序列 `01000001`，不是文本字符“4”和“1”。文件就是一串这样的字节值。文本、图片、可执行程序，交给压缩器之前都会成为字节序列。文本还需要字符编码：在 UTF-8 中，一个字符可能占几个字节。这里的压缩方法不要求输入是可打印的字母。

我们的任务是生成另一串字节，再**逐字节、连同长度一起**恢复原串，包括其中的所有零字节。这叫无损压缩。接收者必须恢复这里的八个字节，不能只得到一段看起来一样的文字。把原始字节叫作 `input`，压缩数据包叫作 `packet`，恢复的字节叫作 `output`，往返目标就是 `decode(encode(input)) = input`。

把输入照抄到数据包中，容易恢复，却没有节省空间。把它替换成“A 和 B 交替，共八个字节”，人能看懂，计算机却遇到了新问题：A 和 B 怎样表示？八表示字节数还是重复次数？指令到哪里结束？如果原文恰好含有指令使用的标点怎么办？压缩格式必须用精确规则回答这些问题，不能让接收者猜测发送者的意思。

这里有两种不同的机会。重复字符串可以换成指向先前字符串的引用；出现次数不同的符号可以使用长短不同的位编码。我们将同时使用这两种方法。它们解决的问题不同，因此必须看清第二步接收的究竟是哪一种表示。

任何无损方法也不可能把所有输入都变短。一字节的输入有 256 种，而长度为零的字节串只有一种。不同输入必须有能区分开的描述，否则不能唯一恢复。长度更大时，同样的计数困难仍然存在。实用压缩器利用部分输入的规律，也接受另一些输入被元数据撑大的结果，最终比较的是整个传输表示的大小。

## 把重复字节换成指令 {#lz77}

先看一个源串已经完整存在的例子 `ABCABC`。直接写出前三个字节后，接收者已经有 `ABC`。此时无需再发送一次 `ABC`，只要发送“向后找三个字节，再复制三个字节”。直接写出的一个字节叫作**字面量**。复制指令叫作**向后引用**，也叫匹配。它的**距离**说明源位置离下一个输出位置有多远；**长度**说明要生成多少个字节。

```text
原文：  A B C A B C
指令：  字面量 A，字面量 B，字面量 C，匹配（距离 3，长度 3）
恢复：  A B C → A B C A B C
```

上图中的指令依次是字面量 A、字面量 B、字面量 C，以及距离 3、长度 3 的匹配。两个数字缺一不可。距离 3、长度 2 只会生成 `AB`；长度 3、距离 2 则会生成 `BCA`。距离相对于匹配开始时的输出位置计算，不是文件中的绝对地址，也不指向压缩包。编码端和解码端可以把存储放在不同位置，仍然对同一串字节达成一致。

这一类方法叫作 **LZ77**。压缩器在先前的原始字节中寻找有用的出现位置，选择写字面量还是匹配。解码器无需重新搜索，只需执行数据包里实际发送的指令。同一输入可以有多种指令序列。例如，`ABCABC` 也可以表示成六个字面量。以后，编码器正是利用这种自由，在搜索耗时和压缩率之间取舍，而无需修改解码规则。

### 复制可以为自己生成后续的源字节 {#overlap}

回到 `ABABABAB`。输出两个字面量后，已有 `AB`。能不能马上用一个匹配描述剩下六字节？可以：距离 2，长度 6。开始时只有两个源字节，因此必须准确规定复制顺序：从**当前**输出末尾向后数给定距离，读一个字节，把它追加到输出，再重复。每次追加都会移动末尾。

| 正在追加的位置，从零计数 | 读取的源位置 | 读到的字节 | 追加后的输出 |
| --- | --- | --- | --- |
| 2 | 0 | A | `ABA` |
| 3 | 1 | B | `ABAB` |
| 4 | 2 | A | `ABABA` |
| 5 | 3 | B | `ABABAB` |
| 6 | 4 | A | `ABABABA` |
| 7 | 5 | B | `ABABABAB` |

写位置 4 时，读的是这个匹配刚在位置 2 写出的字节。这叫**重叠匹配**。它表示一系列前后依赖的单字节复制，不是从某个已有的六字节快照整体搬运。重叠规则不同的批量复制函数不能直接替代它。即使先复制到临时缓冲区，开始时也没有六个已存在的源字节可供读取。

下面这段小型 JavaScript 中，`output` 是可增长的字节数组，`distance` 和 `length` 是匹配的距离和长度。每次追加之后，下一次读取都会重新计算源下标：

```js
if (distance < 1 || distance > output.length || length < 3)
  throw new Error("invalid match");
for (let i = 0; i < length; i++)
  output.push(output[output.length - distance]);
```

这里规定长度至少为三，这是教学编码器采用的规则，也是 DEFLATE 能表示的最短匹配。距离检查保证第一次读取指向已经存在的字节。此后的源位置一直位于增长中的输出末尾之前，即使长度超过距离也成立。距离零不能表示“重复最后一个字节”：它指向尚未写入的位置。重复最后一个字节应使用距离 1。

于是，八个字节变成三条指令：

```text
字面量 A，字面量 B，匹配（距离 2，长度 6）
```

也就是字面量 A、字面量 B，以及距离 2、长度 6 的匹配。这是有用的中间表示，却还不是压缩后的字节序列。“字面量”和“匹配”这些种类、两个整数、消息结束的位置，都还需要表示。如果每条指令都保存成一个很大的程序对象，它占的内存可能比原文还多。要节省空间，还得继续设计传输表示。

### 让简单编码器实际选择指令 {#naive-search}

先用最直接的搜索办法。站在下一个尚未编码的输入位置，逐一尝试距离 1 到当前位置的每个候选。对每个距离，从这里开始向前比较原文字节与该距离之前的字节，直到不相等或到达输入结尾。比较可以越过当前起点：这正对应刚才的顺序复制语义。保留最长匹配，长度相同时选择距离最近的那个。长度至少为三就发出匹配，前进整个匹配长度；否则发出一个字面量，只前进一字节。输入用完后追加结束标记。

在位置 2 的 `ABABABAB` 中，距离 1 立即失败，因为 A 与前面的 B 不同；距离 2 连续比较出六字节，直到输入结尾，于是选中长度 6、距离 2。编码器拥有完整原文，可以直接比较那些字节。解码器没有原文，必须按先前表格依次生成它们。教学交互采用的正是这套搜索和最近距离的平局规则；它容易理解，却会反复检查大量候选，下一篇才能具体说明要优化哪些工作。

## 让常见指令使用更短的编码 {#huffman}

假设某个指令字母表中有四个符号，出现次数分别为 8、4、2、2。这里的**字母表**指全部可能符号的集合，不限于英文字母。暂时把这四个符号叫作 P、Q、R、S。固定两位的编码 `00`、`01`、`10`、`11` 足以区分它们，十六次出现共需要 32 位。

根据出现次数，可以做得更好：P 使用 `0`，Q 使用 `10`，R 使用 `110`，S 使用 `111`。有效载荷需要：

```text
8 × 1 + 4 × 2 + 2 × 3 + 2 × 3 = 28 位
```

也就是 28 位。节省来自那个最短的编码使用了八次。这个计算中的 P 和 Q 是抽象符号，不是把前例的 A、B 换了名字。

编码长短不同，会带来边界问题。如果某个符号是 `0`，另一个是 `01`，看到第一个零时，接收者不知道一个符号是否已经结束。刚才选择的编码避开了这一困难：没有哪个编码是另一个编码开头的一段，也就是**前缀**。可以把全部编码画成二叉树：根是尚未读取任何位的位置，零和一各选择一条分支，叶子标出一个完整符号。这样的前缀码可以从左向右读取：沿树走到叶子，输出对应符号，再从树根开始读下一个。例如 `010110111` 只能切成 `0 | 10 | 110 | 111`，恢复 P、Q、R、S。空格只用于讲解，数据包不需要它们。

**Huffman 编码**根据频率构造这样的树。一开始，每个用到的符号各是一片叶子，权重是出现次数。反复合并当前最轻的两棵树。为使教学编码器遇到平局时也有确定结果，同权重时优先选择叶子最小符号编号更小的树。先把 R:2 和 S:2 合成权重 4 的子树，再把它与 Q:4 合成权重 8 的子树，最后与 P:8 合成权重 16 的根。四片叶子的深度分别是 1、2、3、3。给分支标上零和一，就能获得这些长度的前缀码。

加权路径长度说明了这一构造要优化什么。每次合并两棵子树，其中每次符号出现都增加一位编码。把这次额外开销放在较轻的子树上，能让常见叶子靠近根。在没有最大码长等额外限制的二进制前缀码中，Huffman 方法使给定频率的有效载荷加权长度最小。但它不保证整个文件在所有设计中最小：头部、码表描述、匹配选择和格式的码长限制，都还会产生代价。

### 频率属于正在编码的那一种表示 {#symbol-frequencies}

LZ77 和 Huffman 利用不同规律。LZ77 利用顺序：`ABABABAB` 中有重复字符串。Huffman 利用符号次数的不均衡。重新排列一段数据，只要次数不变，在同一码表下的 Huffman 有效载荷大小就不变，却可能破坏长匹配。反过来，即使难以找到有用的长重复，只要符号次数足够不均衡，Huffman 仍可能获益。

经过 LZ77 后，Huffman 应描述已经选好的指令，不能再把原来八个字节数一遍。我们的小格式把 0 到 255 号符号留给字面量，256 号表示“后面是匹配”，257 号表示结束。**这两个标记编号属于教学格式，DEFLATE 使用不同编号。** 匹配标记之后还有距离和长度，我们的简单格式会直接保存这两个数字。结束标记告诉接收者停止读取指令。

对 `ABABABAB` 已选定的指令序列，Huffman 看见的是 A 一次、B 一次、匹配标记一次、结束标记一次。它不是看见四个 A 和四个 B。四片等权叶子都可以使用两位编码，因此这里的 Huffman 部分没有频率不均衡带来的好处。但 LZ77 已经把重复字节压成了一条复制指令。更长的输入中，如果选出了很多匹配，匹配标记就可能更常见，从而获得更短的码。

这个区别也能避免混淆大小。三条 LZ 指令、包含结束标记的四个 Huffman 符号、八个恢复字节，以及最终数据包的字节数，是四种不同的计数。匹配的距离和长度还要占用额外有效载荷位。下面会把这些开销全部算进去。

## 发送足够的信息，让接收者重建码表 {#codebook}

接收者没有见过原文、原文频率或编码器的树。“使用 Huffman 编码”并没有告诉它 `0` 代表哪个符号。如果只在编码器内部建好树，然后只发送有效载荷，压缩方法还没有完成。

有两种直接的办法。一种是双方事先约定固定码表，另一种是在包中携带本包所选码表的描述。教学编解码器采用第二种：传输每个已用符号的编码长度，再按双方同意的确定性规则分配编码。接收者不需要原始频率，也不需要知道树是按什么顺序合并出来的。

这个规则叫作**规范编码分配**。先按码长从短到长排序，同一码长内再按符号编号从小到大排序。第一个符号使用相应位数的全零编码。处理后续符号时，先把前一个编码当作二进制整数加一；如果新码长更长，就在后面补足零。位宽本身是编码的一部分，`0` 和 `00` 不是可以互换的写法。

对 P:1、Q:2、R:3、S:3，且符号顺序如上，计算过程是：先得到 `0`；加一得 1，补一位零成为 `10`；加一得 3，再补一位零成为 `110`；再加一成为 `111`。只要双方使用这条规则，树图中先前怎样选择左右分支就不再重要。

实际例子中，A 的符号编号为 65，B 为 66，匹配标记为 256，结束标记为 257，码长都是二。排序后得到：

| 符号含义 | 符号编号 | 传输的码长 | 重建的编码 |
| --- | --- | --- | --- |
| 字面量 A | 65 | 2 | `00` |
| 字面量 B | 66 | 2 | `01` |
| 后面是匹配 | 256 | 2 | `10` |
| 消息结束 | 257 | 2 | `11` |

包中的码表只保存编号和码长，最后一列由接收者独立重建。如果另一份输入用到了值为零的字面量，它的编号就是零，也有自己的码表条目。原始字节不会与控制标记混淆，因为标记编号不在 0 到 255 之间。

不是任意码长列表都能组成前缀码。例如，三个长度为一的码无法容纳，因为一位编码只有两种。解码器检查码长范围，检查是否把二叉树填得过满；对多符号码表，这个教学格式还要求完整填满。等价地，把每项的 `2^(-码长)` 相加，应恰好等于一。四项长度都是二时，结果是 `4/4 = 1`。单符号情况单独处理：空输入只有结束标记，给它一位长的编码 `0`。这样不必使用无法在输入中定位的零位编码。

码表自身也有代价。这个刻意简单的表示中，每个已用符号占三个头部字节。很小的自定义码表，可能比它省下的全部有效载荷还大。因此，实用格式必须认真设计码表描述，也要考虑何时改用固定码表。

## 规定整个包，而不只是有效载荷 {#packet}

现在可以写出一套字节级规则，让另一份实现独立解码。这是编码器与解码器共同约定的**教学格式**。它的数据包不是 DEFLATE、zlib 或 gzip 数据流，不能交给 zlib 的解码器。交互最多接受 512 个原始字节，也会拒绝声明输出超过 512 字节的数据包，让搜索过程和完整轨迹保持可读。

数据包从字节边界开始，依次包含原始字节数、码表条目数、码表条目和已编码的指令。计数与符号编号都用两字节无符号整数，采用**大端顺序**，即高字节在前、低字节在后。因此八写成 `00 08`，256 写成 `01 00`，257 写成 `01 01`。

每个码表条目包含两字节符号编号，随后是一字节码长。条目按符号编号递增排列，每个使用的符号恰好出现一次。码长范围为 1 到 32，必须包含结束标记。重建规范码时，可能需要重新按“码长、符号编号”排序，因为传输的条目本身只按符号编号排序。

最后一个条目之后，有效载荷从下一个字节的最高位开始填充，下一位填到紧邻的较低位置。跨过字节边界后，从新字节的最高位继续。这个**高位先行**的规则同时用于 Huffman 编码和匹配数字。指令之间，以及匹配数字之前，都不插入对齐位。

如果解出的符号在 0 到 255 之间，就追加这个字面量，再读取下一个 Huffman 符号。如果是匹配标记，就精确读取 16 位作为无符号距离，再读取 16 位作为无符号长度；这两个数字不是 Huffman 符号。下一个 Huffman 编码紧接在这 32 位之后。距离必须至少为 1，且不能超过已经生成的输出长度；匹配长度至少为 3。只有读到结束标记才停止。此时，输出长度必须等于头部声明的计数，最后一字节内剩余的位必须全部是零填充。填充位应少于八位，且不得有多余字节。码字被截断、数字被截断、没有结束标记、非法码表、不可能的距离、输出超量，都是错误。

原始字节计数是额外的边界检查，不能代替结束标记。生成八字节之后直接忽略后续指令，会错误接受不合法的包。结束标记决定指令序列在哪里结束，计数检查它展开的长度，填充把最后几位凑成完整字节。这三者的任务不同。

### 把八字节例子写成包 {#packet-example}

前面四个条目占十二字节，加上四字节前缀，头部是：

```text
00 08 | 00 04 | 00 41 02 | 00 42 02 | 01 00 02 | 01 01 02
8 字节  4 条目     A:2        B:2       MATCH:2      END:2
```

第一项声明原文有八字节，第二项声明码表有四个条目。随后依次给出 A、B、匹配标记、结束标记的编号与码长。

有效载荷也已经完全确定：写出 A 的 `00`、B 的 `01`、匹配标记的 `10`、距离 2 的十六位表示、长度 6 的十六位表示，最后写结束标记的 `11`：

```text
00 | 01 | 10 | 0000000000000010 | 0000000000000110 | 11
```

共有 `2 + 2 + 2 + 16 + 16 + 2 = 40` 位，恰好五字节。把同一串位每八位分组，不加入分隔符或对齐位，得到：

```text
00011000 00000000 00001000 00000000 00011011
   18       00       08       00       1b
```

整个数据包因此有 21 字节：

```text
00 08 00 04 00 41 02 00 42 02 01 00 02 01 01 02 18 00 08 00 1b
```

八个输入字节变成了 21 个包字节。这个结果应如实保留：指令序列虽然紧凑，却不足以抵消显式码表和宽数字的开销。第一次构造的目的是让每个依赖都看得见。即使表示变大，解码含义仍然明确。只有能计算整个文件，压缩率才成为可以讨论的设计问题。

## 只用数据包完成解码 {#decode}

现在把原文、频率统计和已选指令都放在一边。给一个新的接收者的只有这 21 字节，以及上面的格式规则。它先读出期望输出长度 8、码表条目数 4，再读四个条目。根据相同的两位码长和符号顺序，重建出 `00→A`、`01→B`、`10→匹配标记`、`11→结束标记`。

输出一开始为空，有效载荷的位游标从零开始。游标记录已经消费多少个有效载荷位，不是输出位置。Huffman 解码只消费走到叶子所需的位；遇到匹配，暂时改读固定宽度整数，然后再回到同一个 Huffman 树根。

| 步骤 | 本步消费的位 | 随后的有效载荷位游标 | 动作 | 输出 |
| --- | --- | --- | --- | --- |
| 1 | `00` | 2 | 追加字面量 A | `A` |
| 2 | `01` | 4 | 追加字面量 B | `AB` |
| 3 | `10`，随后 16 位距离和 16 位长度 | 38 | 向后找 2 字节，复制 6 字节 | `ABABABAB` |
| 4 | `11` | 40 | 读到结束标记，检查长度和填充 | `ABABABAB` |

第三步的数字读取会跨过字节边界。如果按“接下来的两个字节”读取，就错了：距离起始于有效载荷已经消费六位的位置，并没有对齐字节。位读取器必须保留游标，逐位收集十六位。收到的数字仍然是 2；把它写作 `00 02` 只是说明它在字节对齐时的数值表示，不意味着可以跳到下一个字节再读。

匹配严格按照先前表格中的六次依赖复制展开。此时长度已经达到八，接收者仍要继续读结束标记。游标最终等于 40，没有剩余填充位或多余字节，于是接受数据包，返回恢复的八字节。整个过程不需要向编码器索取树，也不需要查看原文来选择匹配。

下面的伪代码展示一种解码组织方式。`readSymbol` 从树根出发，用当前位游标沿规范码分支走到叶子；`readBits(16)` 按约定的位序读取无符号整数。进入循环前，头部解析已经构造好码表；最后的检查确认结束标记之后只剩允许的零填充。

```text
output = []
重复：
    symbol = readSymbol(book)
    如果 symbol == END：退出循环
    如果 symbol < 256：把 symbol 追加到 output
    否则：
        distance = readBits(16)
        length = readBits(16)
        检查 1 <= distance <= output.length 且 length >= 3
        重复 length 次：追加 output[output.length - distance]
    检查 output.length <= expectedLength
检查 output.length == expectedLength
检查剩余部分只有到下一个字节边界的零填充
```

伪代码中的每项检查，条件不成立就报错。每次读取还必须在位不足时报错，而码表已经排除了字面量、匹配标记、结束标记以外的编号。循环之所以短，是因为格式已经消除了歧义：标记决定下一步解析什么，前缀码决定符号边界，固定宽度决定数字边界，结束标记决定消息何时完成。

### 修改输入，查看每一层表示 {#codec-scene}

下面的交互运行独立编写的教学编码器，以及只接收序列化数据包的另一套解码过程。**指令轨迹**按原有顺序列出字面量和匹配；**码表**显示传输的码长与重建的编码；**数据包视图**显示真正交给解码器的字节；**解码轨迹**显示位游标和恢复输出怎样前进。“编码并从头查看”会从可编辑输入重新生成这些视图。“下一步”依次查看指令、码表、数据包和接收端写入；“上一步”或位置滑块可以回看这次已完成运行的先前步骤。

先用 `ABABABAB`，再试 `ABCABC`，比较没有重叠的匹配；或者输入 `AAAAAAAA`，观察距离 1。十六进制输入能表示任意字节值，每两位数字提供一个字节。空输入仍然需要包含结束标记的码表，以及它的一位有效载荷编码。也可以试试彼此无关的字节：即使找不到有用匹配，头部开销仍然存在。

## 对照真正的 DEFLATE {#deflate}

zlib 是实现压缩与解压缩的库，核心压缩数据格式叫作 **DEFLATE**。在 zlib 的命名中，`deflate` 是压缩器，`inflate` 是解码器。DEFLATE 同样结合 LZ77 风格的匹配与 Huffman 编码，但使用比教学包更紧凑、也有精确标准规定的表示。现在可以借助已经理解用途的对象，解释两者的区别。

### 两个字母表表示匹配的数字 {#deflate-alphabets}

DEFLATE 不发送一个通用匹配标记，再附上两个十六位数字。它的主要**字面量／长度字母表**同时包含字节值、块结束标记和长度分组。0–255 号是字面量，256 号是块结束标记，257–285 号表示从 3 到 258 的长度。因此，教学格式中的 256 表示匹配，DEFLATE 中的 256 却表示块结束。符号编号必须连同所属格式的字母表一起理解。

长度符号选择一个基础长度，以及紧接着要读的原始**额外位**数量。把额外位的数值加到基础值上，才得到完整长度。长度 6 恰好对应符号 260，不需要额外位。长度 11–12 共用符号 265：基础值为 11，一位额外位区分 11 和 12。因此，长度 12 表示成符号 265，随后一位额外值 1。

长度解出后，下一个 Huffman 符号来自另一个**距离字母表**。合法的距离符号 0–29 用相同的“基础值加额外位”方法描述距离 1–32768。距离符号 1 恰好表示 2；距离符号 4 表示基础值 5，加一位额外位，因此可以表示距离 5 或 6。长度 12、距离 6 的匹配依次成为：长度符号 265、长度额外值 1、距离符号 4、距离额外值 1。之后再回到字面量／长度字母表读取。

分开两张码表，就能分别适应长度分组与距离分组的频率分布。这也使解析没有歧义：字面量／长度符号告诉接收者，应该追加字节、结束块，还是继续读匹配的其余部分。基础值与额外位表是事先已知的格式规则，不从频率推断。固定版本的 [`inftrees.c` 长度和距离表](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/inftrees.c#L70-L86)具体给出了这些分组。

编码端的 [`compress_block`](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/trees.c#L900-L949)正按这个顺序发出：字面量或长度编码、可选的长度额外位、距离编码、可选的距离额外位，最后还有块结束标记。临时记录中的数字已经由匹配搜索选定，但它们不是传输格式本身。

### 块先说明码表从哪里获得 {#deflate-blocks}

DEFLATE 把指令流分成**块**。每块开头的一位说明它是否是最后一块，随后两位说明这块采用哪种表示。块边界可以更换码表，但不会自动清除已经恢复、仍可供匹配引用的字节。解码器要等最后一块也结束，才能判定整条流完成。

**固定 Huffman 块**使用格式规定的码长。字面量／长度符号 0–143 的码长为 8；144–255 为 9；256–279 为 7；280–287 为 8。按符号编号进行规范编码分配，双方无需传输码表描述，就能获得相同编码。286、287 在固定码表中占有位置，但不能表示合法长度。固定距离码表给全部 32 个位置各分配五位编码，其中距离符号 30、31 保留，不能用作匹配距离。

**动态 Huffman 块**在有效载荷之前描述自己的字面量／长度码表和距离码表。它仍然传输码长，仍然重建规范码。为了减少描述开销，它还压缩码长序列，于是增加了一个小字母表：其中符号描述的是码长，不是原文字节。解码器先得到这张描述用码表，再用它恢复两张数据码表，因此没有循环依赖。

具体来说，三位块头之后，动态块先读五位再加 257，得到字面量／长度位置数；再读五位加 1，得到距离位置数；再读四位加 4，得到接下来会提供多少个描述字母表的码长。通常合法的数据字母表最多需要 286 个字面量／长度位置和 30 个距离位置。描述字母表一共 19 个编号，每个提供的码长直接占三位，按照下面的符号顺序传输：

```text
16, 17, 18, 0, 8, 7, 9, 6, 10, 5, 11, 4, 12, 3, 13, 2, 14, 1, 15
```

超过已提供数量的位置，其码长为零，表示不出现。现在按规范规则建立描述码表，用它恰好解出“字面量／长度位置数加距离位置数”那么多个码长。描述符号 0–15 直接给出一个码长；16 用两位额外值表示把前一个码长重复 3–6 次；17 用三位额外值插入 3–10 个零；18 用七位额外值插入 11–138 个零。符号 16 必须已有前一个码长，重复次数也不能超出声明的总数。把恢复出的序列按字面量／长度位置数切开，就能分别重建两张规范数据码表。数据码长最多为 15，块结束符号必须有编码。到这时才能开始解有效载荷。[`inflate.c` 的 `TABLE`、`LENLENS`、`CODELENS` 路径](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/inflate.c#L792-L926)正按这些依赖顺序执行。

第三种合法形式是**原样存储块**。它先跳到下一个字节边界，读取一个十六位长度及其逐位取反的十六位值；也就是用 `65535−长度` 得到第二个数。接收者检查两者是否吻合，再直接复制指定数量的原文字节。这个冗余检查能拒绝不一致的长度字段，不能代替对内容的检查。这些长度字段低字节在前。原样块没有 Huffman 有效载荷，也不需要块结束符号，字节计数直接确定块的结尾。块类型 3 保留。这样的选择，让很难从 Huffman 获益的数据仍有直接的表示办法。

### 用真正的固定块恢复同样八个字节 {#fixed-example}

仍然选择相同指令：A、B、长度 6／距离 2。最后一个固定块包含如下字段。表中的码字按 Huffman 读取顺序书写，即左边第一个字符先被读取：

| 字段 | 含义 | 按读取顺序排列的位 |
| --- | --- | --- |
| 头部 | 最后块标志为 1，固定类型为 1 | `1`，然后 `1 0` |
| 字面量／长度码字 | 字面量 A，符号 65 | `01110001` |
| 字面量／长度码字 | 字面量 B，符号 66 | `01110010` |
| 字面量／长度码字 | 长度 6，符号 260 | `0000100` |
| 距离码字 | 距离 2，符号 1 | `00001` |
| 字面量／长度码字 | 块结束，符号 256 | `0000000` |

有效位总数为 `3 + 8 + 8 + 7 + 5 + 7 = 38`。DEFLATE 从每字节的**低位**向上填充，与教学包不同。多位数字字段先放低位，而 Huffman 码字则按上表列出的码字顺序遇到。这就是不能把每段打印的二进制一律反转的原因。把表中的位依次放进每字节从低到高的位置，最后加两位零以对齐，得到真正的原始 DEFLATE 字节：

```text
73 74 82 40 00
```

解码器读取头部，选用约定的固定码表；再读 A、B，从符号 260 得到长度 6，从距离码表得到距离 2，执行六次前后依赖的复制，最后读取块结束符号。最后块标志说明后面没有下一块。同一段原文现在来自真正的五字节 DEFLATE 流，无需传输自定义码表。这是人为选定的一种合法编码，不是在预测 zlib 的普通压缩器一定会选择同样的匹配和字节。

实际解码器用移动指针表示复制。在直接从当前输出复制的分支，`put` 指向下一个输出字节，`state->offset` 保存解出的距离，源起点就是从 `put` 向后数这个距离。`from` 指向当前源位置，`copy` 记录本段还要追加的字节数。[`inflate.c` 的核心复制循环](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/inflate.c#L1063-L1075)保持了先前推导的逐字节含义：

```c
            do {
                *put++ = *from++;
            } while (--copy);
```

每次赋值先读出源字节，再推进两个指针。循环先前写出的字节，可以在后续迭代中成为源，与距离 2 的表格完全相同。即使高效解码器每次循环处理几个字节，也必须保留这个含义。

## 先提高效率，再扩展任务 {#roadmap}

基本过程现在已经完整：编码器选择字面量和匹配，为得到的符号编码，提供或指定码表，并确定消息边界；解码器重建码表，解析实际收到的位，从自己的输出展开匹配，再识别完成。接收者独立工作之前，每一项都不可缺少。

下一步是效率。逐个搜索所有先前位置很费时；尝试更多匹配可能改善压缩率，也会花更多时间。自定义码表能缩短有效载荷，却可能让小块整体变大。每读一位就沿树走一条边的解码器容易理解，但其中一些工作可以用查表省掉。[下一篇关于时间、内存与压缩率的文章](/read/optimizations.html)从这套完整编解码器出发，推导 `deflate` 和 `inflate` 两侧的取舍。

之后，[第三篇实用功能文章](/read/features.html)再扩展任务：分批接受输入，在输出空间有限时暂停并继续，要求刷新边界，复用字典，以及给 DEFLATE 加上 zlib 或 gzip 封装，用 Adler-32 或 CRC-32 检查恢复出的字节。这些功能建立在这里已经说明的字节转换之上，让相同的压缩机制适应不同应用的交付、复用与完整性需求。
