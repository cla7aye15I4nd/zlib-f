# 工作规则

目标是用 Lean 4 内核检查对上游 zlib `develop` 分支忠实翻译的证明，针对默认 x86_64 Linux 构建。证明范围是 `inflate` 和 `deflate` 的完整安全性（没有未定义行为、没有内存错误、没有泄漏、一定终止）和完整功能正确性。先读 `docs/overview.md`，再读 `docs/spec/safety.md`。证明说明放在 `docs/proof/`。当前状态和剩余工作只记录在 `docs/progress.md`。

三项结论按以下顺序通过验收时，项目即告完成：`inflate` 对任何输入都安全；`inflate` 产生的字节与格式的定义完全一致；`deflate` 安全且其输出可以解码还原为输入。`compress` 和 `uncompress` 作为组合随后完成。gzip 文件接口、回调解码器、仅关于模型的陈述以及其他构建配置不在计划内。`docs/progress.md` 的“范围”一节列出了每个分组及其原因。除非计划内目标需要，否则不要在不在计划内的目标上工作。在诚实工作允许的范围内尽快推进：流程的作用是保证结果诚实，而不是拖慢进度。

## 源码

- `zlib/` 是上游子模块，禁止修改。验证对象是 `zlib/` 加上按名称顺序应用的 `patches/*.patch`。
- 只有已复现且阻碍证明的 zlib 缺陷才允许使用补丁。补丁必须最小化，与已提交上游的修复一致，并列在 `patches/README.md`。上游合入修复且固定版本更新后，删除补丁。
- 翻译与 C 文件一一对应：`zlib/X.c` 对应 `ZlibF/Zlib/X.c.lean`，`zlib/X.h` 对应 `ZlibF/Zlib/X.h.lean`。函数保留 C 名称，文档注释以 C 签名开头。
- 规格放在 `ZlibF/Spec/`。关于 `zlib/X.c` 的证明放在 `ZlibF/Proof/X.c.<主题>.lean`。公开目标的证明放在 `ZlibF/Proof/public-<名称>.lean`。
- 不涉及堆的数学放在 `ZlibF/Math/`。堆、指针、循环和故障等运行时语义放在 `ZlibF/Runtime/*.lean`。

## 翻译

- 逐条语句翻译，禁止重排、合并或简化。
- C 能到达的每一种未定义行为都必须产生 `Fault.ub`。无符号算术回绕，有符号算术接受范围检查。
- 读取未初始化整数时返回任意值，定理必须对所有取值成立。模型把新分配内存中的指针设为 NULL，这比 C 弱。因此证明还必须建立：读取指针字段前已经写入该字段。见 `docs/spec/safety.md` 第 3 节和 `docs/trusted-base.md` 第 2 项。
- 禁止为方便证明而修改翻译。与 C 不一致就是翻译缺陷；修复后还要添加能发现它的差分测试。
- 所有证明都依赖运行时。只有确认与 C 不一致时才修改运行时。

## 已证明的判定

分为两个层级，报告时必须说明是哪一级。

- **已检查。** 定理在 `main` 上，并且该提交的快速门禁通过：全部构建成功，没有 `sorry`，没有禁用构造。Lean 内核已检查该证明。日常工作在这一层级合并。
- **已接受。** 定理还列在 `tests/audit/theorems.txt` 中，并且验收套件在指名的提交上通过：公理检查、目标精确匹配、证明变异和差分测试。只有已接受的结果才能报告为最终结果。

两个层级都适用的规则：

- 只允许依赖 `propext`、`Classical.choice` 和 `Quot.sound`。禁止使用 `sorry`、`native_decide`、`bv_decide`、`axiom`、`implemented_by`、`extern`、`unsafe`、`partial` 或 `opaque`。禁止设法绕过检查；遇到阻碍应报告。
- 只有类型与目标完全相同的定理才算证明了该目标。
- 定理必须明确写出前置条件。如果条件比 `zlib.h` 允许的范围窄，必须在定理注释中说明，并列入 `docs/deviations.md`。禁止悄悄缩小定义域。
- **调用方区域互不相交。** 调用方提供的、在语义上没有理由重叠的内存区域，若能使证明更简单，可以假设完全互不相交：输入、输出、窗口与字典缓冲区，`gz_header` 记录及其 extra、name、comment 缓冲区，以及长度单元。每条这样的前提都必须在陈述中明确写出，并在 `docs/deviations.md` 中占一行；不需要先做 Sanitizer 复现。这不允许按参数值缩小定义域，也不允许丢掉区域不别名时可达的情形。
- **禁止把被调用函数的契约当成假设。** 被调用函数的规格必须由关于该函数翻译的定理建立。初始化函数必须建立表示不变量，并证明它可以成立。只有顶层定理需要具体见证。
- 证明卡住时，必须区分四种可能原因：证明方法、错误规格、翻译缺陷或真实 zlib 缺陷，不预设答案。若怀疑 zlib 缺陷，应构造具体输入，在真实 C 上用 Sanitizer 复现并报告。禁止缩小前置条件来掩盖缺陷。
- 差分测试是翻译忠实性的证据，不是证明。报告时要说明这一点。

## 修正规格、目标或翻译

错误的陈述要修正，而不是绕过。

- 有证据时才修改：经过检查的反例，或有记录的与 `zlib.h` 或 C 源码的不一致。修正放在单独的提交中，说明错在哪里以及原因。
- 把反例作为回归测试保留在 `tests/verification/regressions/` 下。
- 禁止为使证明通过而削弱陈述、缩小定义域或修改翻译。加强过弱的目标是允许且鼓励的。
- 翻译与 C 不一致就是缺陷。修复它，并添加能发现它的差分测试。
- 对 `ZlibF/Runtime/` 的修改要单独提交，并说明原因及受影响的证明。

## 证明工作流程

每一项核心结论（`inflate`、`deflate`）有一个负责人。负责人按以下顺序工作。

1. **先检验陈述。** 在开始长证明之前，先用事实检验目标。用可执行的格式规范与真实的 C 代码在大量输入上对比。在小的具体例子上逐条检查目标的每个条款。在这里发现陈述有误只花几分钟；在证明中途才发现要花几天。按上一节的方法修正。
2. **自顶向下搭骨架。** 在 `skeleton/<result>` 分支上，用具名引理的陈述写出目标的证明，引理的证明先留空。只有骨架分支允许 `sorry`，其他地方都不允许。骨架必须通过类型检查。它就是剩余工作的清单。
3. **公布清单。** 把未完成的引理抄到 `docs/progress.md` 的“核心证明骨架”一节：名称、一句话含义、状态（未完成、已检查）、以小时计的估计。保持更新。
4. **在 `dev` 上逐条完成引理。** 每次证明一条引理并推送到 `dev`。现有证明如果符合引理的陈述就复用。骨架不需要的东西不要证明。
5. **把大定义藏在接口后面。** 表示不变式有一小组接口引理。其他模块使用这些引理，不展开定义。这样修改不变式时只需重建它的接口，而不是几百个模块。
6. **删除骨架用不到的内容。** 绑定在固定参数或默认配置上、无法服务通用引理的证明应当删除，除非某个已登记的定理需要它。
7. **引理之间不要停。** 在里程碑、修正陈述时，或在一条引理上两小时没有进展时才报告。报告写明已检查的内容、提交和剩余估计。

各负责人在不同文件上并行工作。共享构建主机上的重构建一次只运行一个：等另一位负责人的构建结束后再开始自己的。

## 检查

**快速门禁，每次推送和拉取请求都运行**（`build`、`no-sorry`）：全部模块构建成功，没有禁用构造，补丁能应用于固定的 `zlib/`，没有 `sorry`。这是合并的唯一门禁。

**验收套件，每晚在 `main` 上运行，也可按需运行**（`audit`、`difftest`）：公理检查、目标精确匹配、自检、证明变异，以及带和不带 Sanitizer 的差分测试。可通过 `lean` 工作流的手动触发按需运行。夜间运行失败时，要先修复再做新的验收工作，但这不阻止证明工作。

项目不使用锁文件。定义、规范和定理陈述只由 git 跟踪：它的历史就是改了什么、为什么改的记录。保留下来的保护是审计本身：只允许规定的公理，并且目标只能由类型与其完全相同的定理证明。

属于验收的工作在里程碑时批量完成，而不是每次改动都做：

- 在 `tests/audit/theorems.txt` 中登记定理；
- 为每个新证明的公开函数添加证明变异：变异后的翻译（删除检查、差一错误）必须检查失败，且错误位于该函数的证明中；
- 重新生成进度视图。

里程碑是以下之一：`inflate` 证毕、`deflate` 证毕、某个流序列目标证毕，或新增约二十个已检查目标。没有执行的检查，禁止报告为通过。

完整构建占用大量内存。`ZlibF/Proof/crc32.c.lean` 和 `ZlibF/Proof/inftrees.c.lean` 各需 8 到 9 GB。构建时最多四个并行作业，内存上限 16 GB。若某个模块需要更多内存，先查明原因，再考虑提高任何上限。

## 问题记录

已复现的 zlib 问题记录在 `README.md`：简述问题，链接 `docs/findings/` 下的复现材料，并注明证据强度和适用范围。尚未复现的报告留在 `docs/progress.md`。

## 文档

- 文件名使用小写和连字符，例如 `method.md`；`README.md` 和 `AGENTS.md` 保留惯用名称。
- 使用短句，明确说明已经证明的内容、采用的假设和未完成工作。
- 尚待证明确认的 C 解读，标记为 **to confirm**。
- 用 Mermaid 图表达结构和顺序，不要把列表改画成图。
- 不把机器名、地址、用户名、本地路径或工具名写入仓库。

## 协作

- 工作落在集成分支 `dev` 上。提交小而自洽的步骤并直接推送，或在快速门禁通过后立即把拉取请求合并进 `dev`，无需审阅。保持 `dev` 可构建：如果某次推送破坏了快速门禁，先修复它。
- 每到里程碑，在验收套件对该提交通过后，`main` 接收 `dev`。
- 并行工作按不同 C 文件或函数拆分。两个工作者绝不编辑同一个文件。
- 证明全称目标。除非是全称证明的引理，否则不要为固定参数或默认配置添加证明。
- 提交说明描述改动，不添加工具署名行。
- 报告已检查、已接受和未完成的内容，并指明提交。

[docs/anti-cheating.md](docs/anti-cheating.md) 说明为什么绿色构建仍可能毫无价值，以及验收套件防范什么。
