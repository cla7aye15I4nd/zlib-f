## 接受尾部前核对恢复字节 {#checksums}

输入损坏之后，解码器仍可能恢复出完全普通的字节。发送端原本有 `AB`，接收端却得到 `AC`，两者都是合法字节串；仅靠解码指令，无法说明收到的就是原本的内容。因此，在接受完成之前，还要核对恢复出的数据。

发送端对原文字节计算一个短数，放入封装尾部。接收端对恢复字节做同一种计算，再比较两个数。这个数叫作**校验和**。数值不同就发现了损坏；数值相同却不能排除所有损坏，因为许多不同消息可能共享同一个短摘要。它不提供密码学认证。zlib 封装采用 Adler-32；gzip 采用 CRC-32，还核对原文长度模 `2^32`。

实现有两项困难。第一，接收端现在可能只有 `ABABA`，到下一块输出区才收到 `BAB`，必须接着维护同一校验值，不能保存或重读整条消息。第二，长消息中每字节做除法、或逐位做八次运算，代价较大。批处理、查表和按字读取必须得到相同答案，而且恰好读取应该处理的字节。

下面先从需要保留的信息推导两种计算，逐字节算出例子，再引入 C 中的操作与优化。最后把数值步骤连接到可读内存和本次实际输出范围。始终被校验的是原文或恢复出的 `ABABABAB`，不是压缩编码。

### Adler-32：用两个和保留字节值与顺序 {#adler}

增量更新只需要旧摘要和下一段字节。把旧摘要称为**种子**，新的 Adler 序列从种子 1 开始。A 到达后，保留返回的校验和；B 到达时，用这个结果作为下次种子。这叫作在新字节上继续更新。连接独立计算的两个摘要，是另一项操作，下面会在更新规则之后推导。

#### 两个累加器 {#adler-accumulators}

一个累加器记录字节值之和，另一个记录历次累加结果之和。因此，较早的字节会影响更多项。把这两个和称为 `a`、`s`。为了让每个和都能放进结果的一半，计算时取模 `M = 65521`；“取模”就是保留除以 `M` 后的余数。从 `a = 1`、`s = 0` 开始，对下一个字节值 `b` 计算：

```text
a := (a + b) mod M
s := (s + a) mod M
```

第二行使用更新后的 `a`：第一个 A 让两个和都变成 66，接着 B 让它们变成 132 和 198。若 B 损坏成 C，两个和则会变成 133 和 199，校验和随之改变。若 A、B 交换位置，字节和不变，前缀和却会改变。推广到任意输入，把长度记作 `n`，字节值依次记作 `b₁` 到 `bₙ`。取余之前：

```text
a = 1 + b₁ + b₂ + ... + bₙ
s = n + n·b₁ + (n−1)·b₂ + ... + bₙ
```

取余后，两侧模 `M` 的余数仍然相同。第二个式子的权重说明顺序为什么有影响：第一个字节参与全部 `n` 个前缀，最后一个字节只参与一个。

返回的校验和把约简后的 `a` 放在低 16 位，把 `s` 放在高 16 位，即 `a | (s << 16)`。`<< 16` 把 `s` 移到高半，按位或运算 `|` 把这两个不重叠的半部拼起来。这种数值布局与封装中的字节顺序是两件事。zlib 尾部按最高有效字节在前的顺序发送四个校验和字节。

#### 八个字节 {#adler-bytes}

ASCII A 为 65，B 为 66。这个短例子不需要约简：

| 已处理字节 | `a` | `s` | 打包校验和，十六进制 |
| --- | --- | --- | --- |
| 空 | 1 | 0 | `00000001` |
| A | 66 | 66 | `00420042` |
| AB | 132 | 198 | `00c60084` |
| ABA | 197 | 395 | `018b00c5` |
| ABAB | 263 | 658 | `02920107` |
| ABABA | 328 | 986 | `03da0148` |
| ABABAB | 394 | 1380 | `0564018a` |
| ABABABA | 459 | 1839 | `072f01cb` |
| ABABABAB | 525 | 2364 | `093c020d` |

第二个字节使 `a` 变成 `66 + 66 = 132`，使 `s` 变成 `66 + 132 = 198`。第二个累加器不是只加上新字节。因此，这八个字节对应的最终 zlib 校验字段是 `09 3c 02 0d`。

独立逐字节递推与固定版本 C 校验和函数，在这些展示数值上得到相同结果。后面的通用论证再把同一递推连接到实际读取和机器算术。

#### 批次与约简 {#adler-batches}

上表逐字节执行数学规则。对于长缓冲区，每次加法后都取余会反复付出额外开销。先累加、稍后再取余，余数仍然相同，条件是中途机器和不能溢出。因此，zlib 把有界数量的字节步骤放进一个批次。

C 既要保存校验和，也要记录读到缓冲区的哪里。两个累加和分别叫 `adler`（对应 `a`）和 `sum2`（对应 `s`）；`buf` 指向接下来要读的字节，`len` 计数还剩多少字节。数学模数 `M` 在源码中叫 `BASE`。每批至多处理 `NMAX = 5552` 个字节，再对两个和取余；下面会推导这个上限。批次内部的 C 计数器 `n` 计数十六字节组，不是单个字节。宏参数 `i` 是相对 `buf` 的字节偏移；十六步展开依次使用偏移 0 到 15。

下面是单字节宏和完整批次循环的主体，来自[固定版本 `adler32.c` 的 14–18 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/adler32.c#L14-L18)及 [97–106 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/adler32.c#L97-L106)。空行隔开两个节选：

```c
#define DO1(buf,i)  {adler += (buf)[i]; sum2 += adler;}

    while (len >= NMAX) {
        len -= NMAX;
        n = NMAX / 16;
        do {
            DO16(buf);
            buf += 16;
        } while (--n);
        MOD(adler);
        MOD(sum2);
    }
```

`DO1` 读一个字节，先加进第一个和，再把更新后的第一个和加进第二个和。`DO16` 按顺序展开十六次。`while` 条件确认还有完整一批，才减少 `len`。`n` 计数该批的十六字节组；每组处理后，`buf` 前进 16。`--n` 在这些组完成后结束内循环。最后两行 `MOD` 对和取余；所选默认分支中，两者都展开为 `% BASE`。证明必须把这些指针前进、延迟取余与逐字节规则联系起来，不能直接用简单规则代替 C。

为什么 `NMAX` 选择 5552 字节？把上次取余后处理的字节数记为 `m`，与 C 中计数组数的 `n` 区分。从已约简、各自至多为 `M−1` 的分量开始，每个字节最多为 255，第二个和满足：

```text
s ≤ (m + 1)(M − 1) + 255·m(m + 1)/2
```

第一项涵盖起始第二个和，以及起始第一个和的 `m` 次贡献。末项涵盖按 `m,m−1,…,1` 加权的最坏字节贡献。当 `m = 5552` 时，右侧为 `4294690200`，小于 `2^32 − 1`。当 `m = 5553` 时，它变成 `4296171735`，超过该上限。这就是源码选择 `NMAX = 5552` 的原因。

证明义务沿同一依赖展开：每步之后，第一个和与前缀和仍分别同余于逐字节递推。十六步展开按源码顺序保持这份关系十六次。不溢出的界让它描述实际机器累加和，随后的取余再保持同一关系。

每个完整批次执行 347 组，每组 16 个字节步骤。展开分组减少循环开销，同时保留每个新 `a` 到 `s` 的依赖。余下的数据先按 16 个字节分组，再逐字节处理。独立的短输入和单字节路径避免不必要的准备工作。

所选构建使用称为 LP64 的 64 位数据模型：指针和 `unsigned long` 都是 64 位，因此累加和比上面的 32 位界有更大余量，但实现保留相同的批次大小。另一个可选源码分支利用 `2^16 ≡ 15 (mod 65521)` 替代除法。该恒等式解释了为何可以把高位折回低位，却不表示那个分支属于这里描述的默认执行。

#### 缓冲区边界 {#adler-chunks}

回到先交付 A、再交付 B 的解压器。第一次从 1 开始更新，返回 `00420042`。把这个返回值作为第二次种子，函数就把它拆回 `a=66,s=66`。读入 B 后返回 `00c60084`，恰好是 AB 的普通校验和。若第二次重新从 1 开始，得到的只是 B 的 `00430043`，A 的贡献就丢失了。

因此，应用输入的拆分点不必与批次边界一致。一次调用可以在一个字节后结束，下一次继续使用打包、约简后的两个和。校验和状态描述已接收的字节，不描述它们由多少次调用提供。

校验和函数自身不分配、不保留调用者指针，也不写入输入。外层压缩器或解压器另外决定哪些新处理的字节应计入封装校验和。

#### 独立分块 {#adler-combination}

假设两个工作单元已各自从 1 开始算出 A、B 的校验和，只留下这两个数。这里的工作单元可以是两个线程，也可以是分别处理两个文件分块的程序。把 B 的校验和传作更新种子，并不能连接两者：更新函数接收的是字节，不是第二个校验和。组合函数则利用两个摘要和第二段长度，算出连接后的校验和，不必重读任何一段。

推广到先 X 后 Y，把独立计算的分量记作 `(aX,sX)`、`(aY,sY)`。用 `n` 表示 Y 的字节长度，`(aXY,sXY)` 表示要得到的连接结果。则模 `M` 有：

```text
aXY = aX + aY − 1
sXY = sX + sY + n·(aX − 1)
```

减一去掉 Y 多带的一份初始值。长度项表示：X 的字节和会对 Y 中每一个新前缀作出贡献。这里需要的是 Y 的长度，不是 X 或两者之和。

当 X=A、Y=B 时，分量分别为 `(66,66)`、`(67,67)`。取 `n=1`，结果为 `(132,198)`，仍是 `00c60084`。Y 很大时，实现先把它的非负长度模 65521 约简，不需要扫描 Y。Adler 组合使用这种带长度权重的算术，而不是 CRC-32 使用的多项式幂。

#### 校验和入口 {#adler-entries}

C 接口用两种字节计数宽度提供同一更新操作。处理大缓冲区时，计数必须能表示完整长度：

[`adler32_z`](/reference/functions/adler32_z.html) 使用 `z_size_t` 字节计数，在所选构建中为 64 位；[`adler32`](/reference/functions/adler32.html) 使用 32 位计数。大计数应使用多个更新调用或更宽的入口，不应先截断。

[`adler32_combine`](/reference/functions/adler32_combine.html) 和 [`adler32_combine64`](/reference/functions/adler32_combine64.html) 使用 Y 的有符号长度，组合独立开始的校验和。负长度返回 `0xffffffff`。真正的空 Y 校验和为 1，会保持 X 的校验和。

这里的“种子”是更新之前传入的校验和值。正常的接续种子来自先前的计算结果；任意种子则是调用者提供的整数，未必对应真实前缀。NULL 表示没有提供输入指针。精确的 NULL 和任意种子情况很重要：本项目的 Adler 初始化查询要求 NULL 配合零长度。伪造种子不一定遵循规范的单字节递推。下面的分支顺序论证会解释这些情况；它们属于精确数值结果，不能藏进普通递推的前提里。

[公开 Adler 更新命题](/reference/source/ZlibF/Proof/public-adler-update.html#L36) 对所有已表示的可读区间和全部种子字，给出精确返回值与整个堆不变的结论，并覆盖显式的零长度 NULL 查询。“全部种子”使用下面的精确标量结果，并不把任意传入字都解释成真实前缀的校验和。

[公开 Adler 组合命题](/reference/source/ZlibF/Proof/public-adler-combine.html#L118) 对两种长度入口给出终止的标量执行，包括负长度拒绝。连接结论还要求两个参数的低 32 位分别描述真实分块，有符号长度等于第二段长度。参数额外携带高位，不会使这项真实校验和结论失效。

#### 把计算接回解压流程 {#adler-integration}

计算得到 `ABABABAB` 的 Adler-32 为 `093c020d`。回到五字节输出空间的例子：先对 `ABABA` 更新，再接着更新 `BAB`，仍应得到这个数；zlib 尾部存放的正是 `09 3c 02 0d`。分批更新的意义在于保持同一份原文的摘要，而不是为每个输出缓冲区生成一个独立结果。

### CRC-32：用比特保留多项式余数 {#crc}

gzip 用另一种计算完成相同的数据核对。它不保留 Adler 的两个和，而是保留一个 32 位值，通过移位和位比较改变它。其中异或把相同的两位变为零、不同的两位变为一。新的公开 CRC 从零开始，返回值同样足以继续处理下一个缓冲区，所以先处理 A 再处理 B，必须与一起处理 AB 得到同一答案。

先从一个位步骤看清这份状态，再由它推导字节表，以及能让多项工作独立推进的交织字计算。多项式语言则解释这些变换与独立分块组合，为什么仍保留同一结果。

#### 反射寄存器 {#crc-register}

计算需要用少量状态概括已经处理过的所有字节。这个状态保存在一个 32 位工作值中，称为寄存器 `r`。每一步把它右移，移出最低位。如果移出的位为一，还要把常量 `0xedb88320` XOR 到右移结果中。XOR 是按位异或：相同的位得到零，不同的位得到一，没有进位。式子里的 `>> 1` 表示右移一位，`r & 1` 只保留最低位，用来判断它是否为一。`0x` 是十六进制常量的前缀。把这样一步称为 `T`：

```text
T(r) = (r >> 1) XOR 修正值
修正值 = 0xedb88320，当 r 的最低位为 1
修正值 = 0，当 r 的最低位为 0
```

消耗下一个字节时，把其值记作 `b`，先将它 XOR 到寄存器的低八位，再应用八次 `T`。字节的最低有效位先进入计算。这就是反射位约定：计算向低位推进。

公开的运行中校验和是内部寄存器的按位取反值：每个零变成一，每个一变成零。新公开校验和从 0 开始，因此工作寄存器从 `ffffffff` 开始。函数先对传入校验和取反，处理字节，再对结果取反。调用者将返回值直接传给下一次更新；再次自行取反会改变计算。

这个常量由 CRC 的多项式规则决定。可以把寄存器各位看成只能取零或一的系数，此时多项式加法就是 XOR。这种算术称为 GF(2)。CRC 多项式的次数为 32，最高项 `x^32` 在保存的常量中隐含不写。连接独立分块时会用到这种解释；理解单字节计算只需要上面的右移和 XOR 规则。

#### 一个字节 {#crc-one-byte}

对 ASCII A，`b = 0x41`。从公开校验和零开始，内部寄存器为 `ffffffff`。XOR 字节后得到 `ffffffbe`，再执行八个位步骤：

| 已完成位步骤 | 内部寄存器，十六进制 |
| --- | --- |
| 步骤之前 | `ffffffbe` |
| 1 | `7fffffdf` |
| 2 | `d2477ccf` |
| 3 | `849b3d47` |
| 4 | `aff51d83` |
| 5 | `ba420de1` |
| 6 | `b09985d0` |
| 7 | `584cc2e8` |
| 8 | `2c266174` |

第一步移出的位为零，因此只右移。下一步先把 `7fffffdf` 右移为 `3fffffef`，再 XOR `edb88320`，得到 `d2477ccf`。对第八步的结果取反，得到公开 CRC `d3d99e8b`。

现在让第一个缓冲区在 A 后结束。返回的 `d3d99e8b` 就包含继续计算所需的全部状态。把它传给处理 B 的下一次更新，得到 AB 的 CRC `30694c07`。从零独立处理 B 则得到 `4ad0cf31`，这个数本身没有 A 的贡献。独立递推与固定版本 C 函数在这些例子上相符；后面的通用论证还会覆盖码表、按字读取和任意传入种子。

#### 字节表 {#crc-tables}

每个字节都执行八次右移和条件 XOR，有许多重复工作。低字节的贡献只有 256 种可能，可以预先算出，存入称为 `table` 的数组。下面，`i` 是其中一个字节值，`T⁸` 表示执行八次位步骤，`byte_step` 表示消耗一个字节后的工作寄存器：

```text
table[i] = T⁸(i)
byte_step(r,b) = (r >> 8) XOR table[(r XOR b) & 255]
```

寄存器的高 24 位向下移动，表则提供低字节对应的多项式贡献。之所以可以拆开算，是因为这些步骤保持 XOR：先把两数 XOR 再推进，等于分别推进后再 XOR。对 A，索引为 `be`，`table[be] = 2cd99e8b`。与 `00ffffff` XOR，仍然得到 `2c266174`。

在 C 中，`buf` 指向下一个输入字节，`len` 是剩余字节数，`crc_table` 是这张有 256 个条目的表，局部变量 `crc` 保存内部寄存器。计算过程中，它与公开校验和值不同。实际使用表的字节尾循环，来自[固定版本 `crc32.c` 的 934–940 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L934-L940)：

```c
    while (len) {
        len--;
        crc = (crc >> 8) ^ crc_table[(crc ^ *buf++) & 0xff];
    }

    /* Return the CRC, post-conditioned. */
    return crc ^ 0xffffffff;
```

`len` 是剩余字节数；循环条件确认还有字节，才减计数并读取。`*buf++` 读出该字节，再前进指针；XOR 和 `& 0xff` 形成 0 到 255 范围内的表索引。`crc >> 8` 把旧寄存器的高位移下来，`^` 再合入表中贡献。返回语句翻转低 32 位，恢复公开约定。之前的[第 635 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L626-L635)已执行 `crc = (~crc) & 0xffffffff`，所以循环里的局部 `crc` 是工作寄存器，而不是公开值。

[`get_crc_table`](/reference/functions/get_crc_table.html) 暴露这张字节表。它的约定给出静态指针和全部 256 个字节步骤条目。这些条目描述内部寄存器更新，不包含公开接口的取反。返回的存储是静态只读的；该指针不授权读取相邻交织表、写入条目或释放数组。

#### 字与交织 {#crc-braids}

查表去掉了内部八个位步骤，但每个新字节仍需要上一个寄存器值。为了让多项工作独立推进，所选默认分支把输入按每八字节分组，称为一个“字”，读取时把它看成 64 位整数。实现保留五个交错的运行中值，称为交织通道：每条通道有自己的寄存器，每隔五个字处理一次。从初始对齐字节之后的第一个字开始，给各字从零编号：第零通道处理位置 0、5、10……；第一通道处理 1、6、11……，以此类推。

这些是有间隔的子序列。相应表计入相邻通道字之间的多项式距离。第零通道接收预处理后的传入寄存器 `(~crc) & 0xffffffff`，其余通道从零开始。它们不是连续五个分块的普通校验和。最终块代码通过字递推，按原始字节顺序合并这些贡献。

这个分支不能仅凭还有一个字就安全进入。C 中，`N` 是通道数，`W` 是每个字的字节数。[640–650 行的入口和对齐循环](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L640-L650)先要求 `len >= N * W + W - 1`，再逐字节处理，直到 `((z_size_t)buf & (W - 1)) == 0`。对 `N=5,W=8`，阈值为 `5×8 + 8−1 = 47` 字节。这里的对齐要求输入地址是八的倍数，掩码 `W - 1` 用来检查地址的低三位。最多处理七个字节就能到达这样的地址，至少留下一个 40 字节块。

一块包含每条通道各一个字，因此占 `N × W = 40` 字节。C 计数器 `blks` 表示还剩多少完整块，其中包含最后一个留给合并的块。[第 710 行的块循环](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L706-L728)使用 `while (--blks)`，只处理最后一块之前的所有块。独立代码处理最后一块及其合并。提前保留至少一块，才能避免第一次前减下溢。之后剩余不足 40 个字节，由展开的字节尾部和逐字节循环处理。

要在 C 中看见这些独立依赖，可以沿小端分支的第零通道读下去。`words` 是按八字节的字寻址的输入指针；`crc0` 是第零通道的运行中寄存器，`word0` 暂存它与下一个输入字的 XOR。`crc_braid_table` 为字内部的每个字节位置准备一行，`k` 选择其中的位置。下面选取[第 712 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L710-L720)、[728–732 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L728-L732)和 [748–765 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L748-L765)中属于该通道的语句。省略了夹在中间的其他通道语句及其预处理条件，这不是完整循环：

```c
                word0 = crc0 ^ words[0];

                words += N;

                crc0 = crc_braid_table[0][word0 & 0xff];

                for (k = 1; k < W; k++) {
                    crc0 ^= crc_braid_table[k][(word0 >> (k << 3)) & 0xff];
                }
```

`words[0]` 读取分给第零通道的下一个字；`word0` 把它与该通道原来的 `crc0` 混合。源码相邻各行对 `words[1]` 到 `words[4]`、`crc1` 到 `crc4` 做同样的事。五个字全部读出之后，`words += N` 才把公共指针推进到下一块。每条通道更新只依赖自己的旧值和输入字，因此不必等待另一条通道刚算出的 CRC。

具体看地址路径：把第一个对齐字节的偏移称为 `q`。在所选 `N=5,W=8` 下，第零通道先读取 `q…q+7`，第一通道读取 `q+8…q+15`，第四通道读取 `q+32…q+39`。`words` 前进五个字，就是 40 字节。若还有下一次普通迭代，第零通道接着读 `q+40…q+47`，第一通道读 `q+48…q+55`。同一通道相邻两次取字相隔 40 字节，并不是紧挨着的八字节段。

第一次查表处理 `word0` 的第零个字节位置。`k` 循环通过右移 8 到 56 位，提取位置 1 到 7，分别查表，再把贡献 XOR 到 `crc0`。在这个小端路径上，低字节对应所读字中最早的输入字节。表行 `k` 表示字内部的字节位置，不是通道编号；各通道使用相同各行。交织表已经计入同通道两次取字的间距，与普通单字节表不同。最后，[772–780 行的末块合并](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L772-L780)通过 `crc_word` 依次合入第零到第四通道，在字节尾循环之前恢复成一个寄存器。

这样的组织暴露了相互独立的通道依赖，并分摊循环工作。字的端序和地址对齐仍是选择、解释实际读取的一部分。所选证明模型按目标端序组装相同字节；C 转换和 ABI 对应关系需要各自审查。

#### 多项式算子 {#crc-operators}

如果两个工作单元独立计算了 A、B，又丢弃了字节，该怎样连接？不能把第二个 CRC 当作 B 的数据，拿去更新第一个 CRC。需要先把 A 的贡献推进到 B 占据的字节位置之后，再用 XOR 合入两个贡献。

对于一般的先 X 后 Y，用 `n` 表示 Y 的长度。`CRC(X)`、`CRC(Y)` 表示各自从零开始独立计算的公开校验和，`X ++ Y` 表示连接。用 `T⁸ⁿ` 表示执行前面的位步骤 `8n` 次，即让一个 32 位值前进 `n` 个零字节，不带公开接口取反。于是：

```text
CRC(X ++ Y) = T⁸ⁿ(CRC(X)) XOR CRC(Y)
```

在这个连接恒等式中，初始和最终取反的项相互抵消。不能通过对 `n` 个零字节调用公开更新函数来实现 `T⁸ⁿ`，因为那次调用会包含它自己的取反约定。

当 X=A、Y=B 时，`T⁸(d3d99e8b) = 7ab98336`。与 B 独立计算的 `4ad0cf31` XOR，得到 `30694c07`，即 AB 的 CRC。

前进操作保持 XOR，可以用二进制矩阵表示，也可以用模 CRC 多项式的乘法表示。无论采用哪种表示，保存的是“把已有贡献向后推进指定长度”这一操作，不是第二段的数据或校验和。

所选源码使用多项式乘法。[954–960 行的生成器](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L954-L960)调用 `x2nmodp(len2, 3)`：`len2` 是 Y 的字节长度，辅助函数要计算代表前进这么多字节的幂。第二个参数选择每个长度单位包含的位步骤数；3 选中每字节八个位步骤，因为 `2^3 = 8`。

[184–194 行的辅助函数](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L184-L194)每次检查长度的一位。`x2n_table` 中的幂由反复平方得到；长度位为一时，辅助函数乘入对应的幂，然后右移长度，转到下一个幂。这样不必遍历 `n` 个字节，就能算出 `x^(8n)` 的算子。

例如第二段有 13 字节，`13 = 8 + 4 + 1`。实现选取推进 8、4、1 字节的三个预计算操作，把它们组合起来，效果等于推进 13 字节，也就是 104 个零输入位。它无需真的循环 104 次。这说明长度的二进制位为什么足以驱动计算；预计算表和乘法是否确实实现了这些操作，仍由证明建立。

在这种反射乘法表示中，乘法单位元是 `0x80000000`：与它相乘表示“尚未推进”。这里的乘法是前面介绍的多项式乘法，不是普通整数乘法。

#### 校验和入口 {#crc-entries}

同一个 CRC 更新也有两种字节计数宽度；另外的入口负责独立摘要和可复用的长度算子：

[`crc32_z`](/reference/functions/crc32_z.html) 使用 `z_size_t` 字节计数，在所选构建中为 64 位；[`crc32`](/reference/functions/crc32.html) 使用 32 位计数。[`crc32_combine`](/reference/functions/crc32_combine.html) 和 [`crc32_combine64`](/reference/functions/crc32_combine64.html) 接受独立校验和与 Y 的有符号长度。

许多第二分块长度相同时，可用 [`crc32_combine_gen`](/reference/functions/crc32_combine_gen.html) 或 [`crc32_combine_gen64`](/reference/functions/crc32_combine_gen64.html) 一次生成算子，再通过 [`crc32_combine_op`](/reference/functions/crc32_combine_op.html) 复用。算子由生成函数产生是一项定义域要求，不是只要任意非零整数即可。

负长度生成零，并让组合调用返回零。真正的空 Y 的 CRC 为零，会保持 X 的校验和。若长度为零而参数是任意标量，实现则返回两者低 32 位的 XOR。NULL 更新查询即使长度非零也返回零。这些标量 API 情况与连接保证不同，后者还需要真实分块的校验和，以及正确的第二段长度。

[CRC 更新命题](/reference/source/ZlibF/Proof/public-crc-updates.html#L18) 对全部已表示的可读字节视图、任意种子和允许的 NULL 查询，给出精确值及堆不变。全局表前提把字节表和多项式幂表固定为库初始化后的数值，不允许调用者任意选择查表内容。

[CRC 组合命题](/reference/source/ZlibF/Proof/public-crc-combine.html#L76) 为两个生成器、生成算子的应用和两种组合宽度，建立精确多项式结果，并保持堆不变。标量公式把任意传入校验和投影到低 32 位；要把结果解释为连接后的校验和，还要求这些值与第二段长度描述真实分块。

#### 把计算接回 gzip {#crc-integration}

同一份 `ABABABAB` 的 CRC-32 是 `94b093a4`，与 zlib 使用的 Adler 值不同。gzip 将它按低字节在前写成 `a4 93 b0 94`，再跟上八字节原文的长度字段 `08 00 00 00`。解压端计算的是恢复的原文：若分两次得到 `ABABA` 和 `BAB`，CRC 也要接着更新。

### 把算术连接到实际读取的字节 {#checksum-proof}

尾部比较现在有了数值目标：对 `ABABABAB`，Adler-32 是 `093c020d`，CRC-32 是 `94b093a4`。要有理由使用这些目标，还必须建立：**算出的数恰好描述这次压缩或解压处理的那段原文。**

五字节目标区先得到 `ABABA`，再得到 `BAB`，每一批必须恰好计入一次。重复第一批、漏掉最后一个字节，或从初始种子重新开始，即使每次加法与查表正确，也会得到错误结果。因此，论证要一起跟踪字节切片、运行中校验值和读取指针，再把这份关系交给尾部比较。

下面为了手算清楚，把数据缩短为第一个缓冲区中的 A 与第二个缓冲区中的 B。算法含义、机器算术、内存读取与分块组合，分别解释这两块数据怎样得到同一个整体结果。Adler-32 递推告诉我们最终校验和是 `00c60084`，CRC-32 则是 `30694c07`。但这笔计算本身还不能说明 zlib 恰好读取了每个请求字节一次，把第一次结果接入第二次调用，或者没有越界访问就返回了。C 还为短输入、延迟约简、查表和对齐字读取安排了不同路径。证明必须把每条所选路径连接到同一字节含义。

证明既要描述字节，也要描述程序从哪里读它们。调用者的“堆”记录已有内存对象和其中的内容；指针选中首字节，长度计数本次请求的字节。“种子”是更新之前传入的校验和，正常情况下来自上次调用的结果。这些输入须满足入口明确写出的定义域。结论包含精确返回值和不变的堆。要理解它能为应用保证什么，需要分开三个问题：

| 问题 | 必须建立什么？ |
| --- | --- |
| 调用是否安全运行并结束？ | 每次读取、算术和循环都满足条件，执行返回而没有模型故障。 |
| 它返回哪个数？ | 这个 C 入口的精确数值行为，包括任意种子字、查询和错误情况。 |
| 这个数是否属于原本要处理的数据？ | 种子描述真实前缀，本次恰好处理下一段字节，组合使用真实的第二段长度。 |

即使数值计算完全正确，读错缓冲区仍然只会得到错误数据的校验和。反过来，可读缓冲区配上伪造种子也可以安全执行，但结果未必表示“整个流的校验和”。证明要让这两个区别都可见。

#### 独立递推 {#checksum-proof-model}

第一步是先定义答案，不借用实现的优化。独立的 [格式定义](/reference/source/ZlibF/Spec/Format/Checksum.html) 用逐字节模更新定义 Adler，用逐字节 XOR 和八个反射位步骤定义 CRC。两个定义都不调用翻译后的校验和函数或它的表。因此，即使 C 算错了某张表，也不能让预期答案跟着一起变错。

对字节序列“折叠”，指从种子出发，依次对每个字节应用更新步骤。把第一段称为 X，第二段称为 Y。先在 X 上折叠，再在 Y 上折叠，等于在连接序列 `X ++ Y` 上折叠。这建立模型层的增量含义，尚不能说明指针循环访问了相同列表，或展开算术计算了相同步骤。

```mermaid
flowchart LR
    Memory["可读内存区间"] -->|"抽取请求的字节"| Bytes["独立字节序列"]
    Memory -->|"实际 C 读取与优化更新"| Returned["返回的校验值与不变的堆"]
    Bytes -->|"逐字节数学递推"| Expected["预期校验值"]
    Expected -->|"算术与读取循环证明"| Returned
```

执行在实际堆上补齐这些事实。用 `off` 表示初始数组偏移，`k` 表示已经读取的字节数。循环不变量连接三件事：指针位于 `off+k`；还有字节时，下次读取仍然合法；寄存器表示请求字节的前 `k` 项。初始化在零次读取时建立它，单步保持它，退出时得到完整请求序列。

例如，短 Adler 分支维护两个和：`adler` 累加字节值，`sum2` 累加每次更新后的第一个和。`buf` 指向下一个字节，`len` 计数还剩多少字节。`BASE` 是 Adler 的模数 65521；`MOD28` 是取余宏，在所选默认构建中实现为除以 `BASE` 取余。这个分支实际包含下面几行，来自[固定版本 `adler32.c` 的 85–94 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/adler32.c#L85-L94)：

```c
    if (len < 16) {
        while (len--) {
            adler += *buf++;
            sum2 += adler;
        }
        if (adler >= BASE)
            adler -= BASE;
        MOD28(sum2);            /* only added so many BASE's */
        return adler | (sum2 << 16);
    }
```

`len < 16` 只选择路径，本身不保证 `buf` 可读。`while (len--)` 检查旧计数，因此只有仍有字节时才执行循环体。`*buf++` 先读当前字节，再前进指针；下一行使用更新后的第一个和。旧计数为零时，无符号后减会回绕，但不会再进入循环体；把这个回绕理解成负计数，就改变了 C 的含义。证明把实际循环关联到已读次数这个自然数，再论证余下各行：一次条件减法约简 `adler`，`MOD28` 约简 `sum2`，返回语句把两者装进低半和高半。对单个两字节 AB 缓冲区，两次迭代得到熟悉的 `(132,198)` 分量。若分成两次单字节调用，则会走前面的快速路径；执行证明必须覆盖这两条路线。

#### 机器算术 {#checksum-proof-arithmetic}

循环不变量必须描述机器真正执行的算术。Adler 的数学模数是 65521。机器无符号溢出使用二的幂作为模数。它们不可互换：`2^32 mod 65521 = 225`，因此约简前一次未被发现的 32 位回绕，就可能改变期望结果。“C 允许无符号回绕”只能说明该操作被允许，不能说明结果符合 Adler 递推。

所选 LP64 构建中的指针和 `unsigned long` 都是 64 位，因此 Adler 加法使用 64 位 `unsigned long`。令 `a`、`s` 为尚未约简的第一、第二个和，`j` 为一批中已读的字节数。从掩码后的 16 位种子分量开始，经过至多 5552 个步骤，一个方便使用的界为：

```text
a ≤ 65535 + 255j
s ≤ 65535 + j(65535 + 255×5552)
```

当 `j≤5552` 时，它们给出 `a≤1481295`、`s≤8224215375`，均小于 `2^64`。所以加法与自然数算术一致，再由同余关系支持延迟约简。前面从已约简分量推导的批次上限 `NMAX = 5552` 表示两次取余之间最多处理的字节数，其推导假设 32 位的和与已经约简的分量；这个更宽的界也容纳数值执行论证中的掩码后任意种子。

CRC 使用另一种算术：每个位是取零或一的系数，相加就是不带进位的 XOR，这称为 GF(2) 算术。Lean 中的 `UInt32` 表示 32 位无符号值，对它做 XOR 和逻辑右移，就直接实现了 CRC 的寄存器步骤。表证明必须说明每个条目等于对应的八次多项式位步骤；只证明有 256 个条目，没有建立任何数值含义。字递推还要跟踪加宽临时值、字节顺序和最终 32 位投影。因此，Adler 算术论证的关键是未约简和的界，CRC 的关键是同一位变换的不同表示彼此相等。

#### 内存视图 {#checksum-proof-memory}

接着把字节序列连到内存。`offset` 是首字节位置，`length` 是请求数量，`array.size` 是包含它们的字节对象大小。可读性要求 `offset+length≤array.size`，解引用在终点之前发生。例如，五字节对象中，偏移为 3、长度为 2 时，可以读取位置 3、4；位置 5 只是终点，不能读取。空区间可以使用对象的 one-past 指针，即紧接最后一个字节之后的位置。两个更新都保留整个堆和所有权：只读输入，不分配，也不保留调用者指针。

CRC 的八字节读取需要地址为八的倍数。这不仅取决于数组索引，还取决于对象起始地址。模型让分配的字节块从对齐地址开始；静态和嵌入数组的起始地址除以八，则可以有任意但固定的余数，这就是“原点余数”。[一般字节视图定理](/reference/source/ZlibF/Proof/crc32.c.views.html#L567) 覆盖这些已表示的视图和余数。它不证明一般的机器 ABI，也不覆盖所有有效类型别名。

前面的按字读取路径给五条交织通道各分配一个八字节的字，合起来是一块 40 字节。它的入口阈值为 47 字节：最多处理七个字节就能达到对齐地址，因此仍至少留下一整块。这在执行前减块循环之前非常重要。行索引小于 8，字节索引小于 256，64 位字中的提取移位最多为 56 位。这些事实支持访问；多项式不变量支持表内容和合并的正确性。

流状态结果使用[平台前提](/reference/docs/spec/platform.html)，要求每个已表示字节对象小于 `2^63` 字节；完整流可以跨越许多这样的对象。公开校验和更新结果使用上面的可读视图边界，不添加这个更窄的流状态定义域。[可信基础说明](/reference/docs/trusted-base.html)解释模型按字读取与 C 之间的对齐、转换和别名对应。

#### 组合长度 {#checksum-proof-composition}

继续更新需要字节，组合需要两个校验和及第二段长度。如果 A、B 独立计算过，Adler 组合应得到 `00c60084`，CRC 组合应得到 `30694c07`，期间不读取任何一个缓冲区。证明既要覆盖精确的标量计算，也要把输入关联到真实序列。第二段长度错误仍会算出一个数，却没有连接后的保证。

Adler 组合展开两个独立开始的分量和，去掉重复的初始一，核算第一块对新前缀的贡献。实现对非负长度取余，必须保持这项长度贡献；负长度则走独立的拒绝分支。

CRC 组合要先把第一段的贡献推进到第二段之后。把第二段的字节长度称为 `n`，把一个零输入位对应的寄存器步骤称为 `T`。于是 `T^(8n)` 表示执行 `8n` 次这个步骤，因为每字节有八位。这个前进操作既能用二进制矩阵表示，也能用模 CRC 多项式的乘法表示。

所选源码使用多项式乘法：`multmodp` 的两个输入用低 32 位编码多项式余数，生成的算子则编码所需的 `n` 字节前进操作。`x2n_table` 保存的幂，让实现能够按 `n` 中置位的位置组合出算子，不必执行 `8n` 个独立步骤。证明要把这些预计算幂和每次实际乘法连接到独立的位递推。

终止性具有真实的定义域条件。在[固定版本 `crc32.c` 的 166–175 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L166-L175)，`multmodp` 从位 31 开始扫描。只有找到一个置位、且其下方再无置位时，才可能跳出。如果操作数的低 32 位全为零，扫描掩码不断右移也永远到不了这个跳出条件。因此，任意非零 64 位整数并不足够。

算子生成定理会在乘法之前建立低位所需的事实。因此，[`crc32_combine_op` 契约](/reference/functions/crc32_combine_op.html) 使用生成的算子，包括零拒绝结果。C 的 [969–972 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/crc32.c#L969-L972)在生成算子为零时，先返回零，不调用 `multmodp`。对有效的正算子，证明使用已经证明的乘法结果，不能假定被调函数契约成立。

#### 查询与种子定义域 {#checksum-proof-domains}

种子是调用者传给更新函数的校验和值。短例子通常使用初始种子：Adler 为 1，CRC 为 0。公开数值定理还必须解释其他种子字、空区间和查询参数。这些情况都要按实际分支顺序阅读。

Adler 的 [70–82 行单字节快速路径](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/adler32.c#L70-L82)位于 NULL 检查之前：长度为一时，先读 `buf[0]`，才可能到查询分支。本项目显式的初始化查询定义域是 NULL 配合零长度；该限制记在 [偏离说明](/reference/docs/deviations.html) 中。CRC 先检查 NULL，对任何提供的长度都返回零。非 NULL 的空 CRC 更新保持传入的低 32 位。

Adler 还要区分正常校验和与伪造种子字。对于 `adler32_z(0xfffffff0,"\0",1)`，掩码后的分量为 65520 和 65535。低半的 65520 是第一个和，高半的 65535 是第二个和。加上零字节后，第一个和不变，再把它加进第二个和，得到 131055；一次条件减法留下 65534，产生 `0xfffefff0`。若先完整约简起始分量，高分量则会是 13。这个调用内存安全；朴素的任意种子功能命题却是错的。

数值规格 [`adlerValue`](/reference/source/ZlibF/Spec/Public/Checksums.html#L41) 保留这个单字节行为，并在其他长度下规范化起始值。真实增量种子与普通递推一致。入口宽度、非 NULL 空区间、负组合长度和生成算子需要不同的情况划分。

#### 精确结果 {#checksum-proof-evidence}

更新与组合结果现在给出了同一应用论证的不同部分。可读区间前提说明更新允许读取哪些字节；精确标量结果说明返回哪个数，包括查询和特殊种子行为；独立递推把正常种子和真实分块长度连接到数据序列；静态表结果建立优化代码使用的表值。它们不能相互替代。

把这些结果应用到 C，仍保留所述地址、对齐、转换和别名条件。在外层压缩器或解压器中，最后一步要选中恰好新接受或新恢复的字节，以及对应的封装字段。即使另一段可读区间的校验和完全正确，也不能完成这项义务。

#### 把局部保证交给封装 {#checksum-proof-integration}

更新函数证明指定内存区间的校验值，流式记账给出本次调用实际恢复的精确区间。对这个区间恰好更新一次，暂停时传递返回值，到正确的完成边界再与尾部比较。尾部不匹配因此可以在部分输出已经交给应用之后拒绝消息，却不会擦除那些字节。

使用 gzip 文件操作时，同一关系继续穿过文件缓冲区，连接到返回给应用的原文范围。文件层要记录预读和成员边界，每个成员的校验仍然描述该成员恢复出的数据。这就是局部数值保证怎样参与解码，而不是成为孤立的算术结果。
