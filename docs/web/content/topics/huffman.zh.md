## 从符号次数到可解码的码字 {#connection}

[匹配选择](/verification/matching.html)省去了重复字节，却还留下了待编码的符号。假设已经选定 `A`、`B`、长度 6／距离 2 来表示 `ABABABAB`：发射时仍然需要区分 A、B、长度码、距离码，以及块结束标记。Huffman 编码让常用符号使用短码、少见符号使用长码，同时让接收者能从连续比特中识别每一个符号。

zlib 为字面量／长度和距离分别统计次数、构造编码。长度 6 增加一个长度码的频率，距离 2 增加一个距离码的频率；它们不是六次字节 A 或 B。块结束标记也必须有编码。动态块还需要把这套编码的描述发给接收者，固定块则使用格式预先约定的编码。

这条构造路径服务于动态块。若想先看一组符号怎样真正变成压缩字节，可以直接读[固定块的逐字段例子](/sample/blocks.html#example)，它使用预定义编码；原样存储块则绕过符号编码。动态候选仍会参与成本比较，但并非每个输出块都要发送自建的树。

## 一组可手算的频率 {#example}

只有三个记录的例子适合追踪完整块，却不容易看清频率差异如何改变树形。为此，[合并树的构造](/sample/huffman-tree.html)另选一组抽象符号次数：`A:8、B:4、C:2、D:2`。它表示某一个编码字母表的 16 次符号出现；这里的 A、B、C、D 是树叶标签，不是把前面的八字节输入重新计数。

按较小频率合并，最后得到长度 `1、2、3、3`。加权载荷成本是 `8×1 + 4×2 + 2×3 + 2×3 = 28` 位，少于给四个符号各分配两位的 32 位。不过，这只是符号载荷的比较，还没有支付动态块描述的成本。构造一棵更省载荷的树，并不保证动态块一定获选。

## 从树深度继续到接收者 {#handoff}

[码长限制与编码描述](/sample/huffman-lengths.html)继续使用长度 `1、2、3、3`：双方按相同规则分配 `0、10、110、111`，因此接收者知道 `110` 是 C，也知道从哪里继续读下一项。随后用一个更深的小树说明，为什么超长码不能直接截断，以及怎样通过修复仍保留可解码性。最后把数百项码长变成重复指令，再解释接收者如何重建它们。

[树构造与解码一致性](/sample/huffman-proof.html)把这些步骤连到实际数组和 Lean 结果：叶子不能重复或遗漏，父节点必须先于孩子被使用，长度修复必须保留合法码空间，发射的描述必须还原同一组码长。它也说明，码字可解码与共享存储不被提前覆盖需要不同的条件。

拿到编码以后，主线回到[块选择与输出](/verification/output.html)：将动态描述成本与固定编码、原样存储比较，再为选定记录写出比特。需要看接收端怎样使用这些码长时，可以继续[解压与解码](/verification/decoding.html)。
