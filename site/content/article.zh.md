压缩库接收字节，产生另一串字节。简单的接口背后，是匹配搜索、编码、位缓冲和可以跨调用暂停的状态机。我们先用几个小例子把它们拆开，再追问：怎样确信实际程序做对了这些事？

# 从字节到压缩流 {#how-zlib-works}

<p class="zl-part-intro">从八个字节开始，搭起压缩与解压的过程。</p>

## 字面量与回引用 {#bytes}

看一眼这个字符串：`ABABABAB`。

直接发送它，需要八个字节。另一种做法是先发送 `A` 和 `B`，然后附上一条指令：**从当前输出末尾回退两个字节，逐字节复制，直到新增六个字节。**

这里有两个量：距离是 `2`，长度是 `6`。距离说明从哪里读，长度说明产生多少个字节。它们合在一起，就是一个匹配（match）。没有用匹配表示的单个字节，叫作字面量（literal）。

<div class="zl-token-line"><span>字面量 A</span><span>字面量 B</span><b>匹配 · 长度 6 · 距离 2</b></div>

先不要急着算节省了多少空间。现在我们只是把字节串换成了符号序列；符号还要编码，数据还要放进有头部的容器。对这么短的输入，最后的结果完全可能比原文更长。

不过，我们已经把最重要的问题变小了：只要接收者知道怎样执行这三个符号，就能恢复原文。试着一次只复制一个字节。

<div class="zl-demo-mount"><zlib-demo kind="copy">
  <p>先输出 AB。执行长度 6、距离 2 的匹配，输出依次变为 ABA、ABAB、ABABA、ABABAB、ABABABA、ABABABAB。</p>
</zlib-demo></div>

第一次复制读取最前面的 `A`。第二次读取 `B`。第三次读取的 `A`，已经是这次匹配刚刚写出来的字节了。

所以，这条指令不是“从原有的两个字节里截取六个字节”。它每次从当前输出末尾回退两个位置，读一个字节，再把这个字节加入历史。历史会增长，读取位置也会前进。匹配长度因此可以大于距离。

把距离改成 `1`，就能观察到另一个熟悉的模式：一个 `A` 不断产生新的 `A`。

这就是 DEFLATE 使用的 LZ77 思想：已经出现的内容，可以通过指向历史的描述来重新产生。这里展示的是合法符号的含义，不是实际 zlib 对这个短输入必然采用的编码。

## 库与数据格式 {#layers}

现在可以把名字放回来了。

**zlib 是一个 C 库。** 它提供压缩、解压、校验，以及面向缓冲区和流的接口。核心流式压缩接口叫 `deflate`，解压接口叫 `inflate`。

**DEFLATE 是一种数据格式。** 它规定怎样把字面量、匹配和块编码成比特，以及怎样从比特恢复这些符号。它没有规定压缩器必须怎样找匹配。两个压缩器可以为相同输入选择不同的符号序列，只要都能解出原文。

**zlib 和 gzip 也都是封装格式。** 它们在 DEFLATE 载荷外面添加不同的头部和尾部。无封装 DEFLATE（raw DEFLATE）则只有载荷。

<figure class="zl-layers">
  <div><span>zlib</span><i>头部</i><b>DEFLATE 载荷</b><i>Adler-32</i></div>
  <div><span>gzip</span><i>头部与可选字段</i><b>DEFLATE 载荷</b><i>CRC-32 · 长度</i></div>
  <div><span>raw</span><b>DEFLATE 载荷</b></div>
  <figcaption>封装提供识别、参数和数据校验等信息。校验值可以检测数据损坏，不提供密码学认证。</figcaption>
</figure>

因此，解出最后一个数据字节，不一定就完成了整个流。解压器还可能需要读取块结束码、检查校验值，或者完成 gzip 的长度检查。后面的流式章节会重新遇到这个区别。

格式的原始定义分别见 [DEFLATE / RFC 1951](https://www.rfc-editor.org/rfc/rfc1951)、[zlib / RFC 1950](https://www.rfc-editor.org/rfc/rfc1950) 和 [gzip / RFC 1952](https://www.rfc-editor.org/rfc/rfc1952)。

## 保存近期字节，再寻找重复 {#search}

前面说，压缩器可以用“距离 2、长度 6”代替重复的 `ABABAB`。现在要解决的是：**压缩器读到新内容时，怎样找到以前出现过的相同片段？**

先设想一个没有窗口的做法：把整个文件读进内存，每到一个新位置，就向前寻找重复。这个办法需要保留越来越多的数据。若文件还在持续到达，我们甚至不知道最终要准备多大的内存。

zlib 采用有界的历史：保留近期字节，在这段内容里寻找重复。较老的字节离开范围后，就不再被后续匹配引用。文件可以继续增长，保留历史所需的内存则有上限。

**“滑动窗口”首先是在解决历史该保留多少、怎样复用内存的问题。** 它不是一种单独的编码。最后写入压缩流的仍然是字面量和长度／距离对。

### 随处理位置前进的保留范围 {#window-purpose}

为了看清变化，先用一个只保留最近八字节的示意窗口。已经处理的内容是 `0123ABCD`，接下来是 `ABCDwxyz`。压缩器在保留历史里找到 `ABCD`，于是可以用“回退 4 字节，复制 4 字节”表示接下来的四字节。

接受这条匹配后，已经处理的内容变成 `0123ABCDABCD`。最近八字节是 `ABCDABCD`，最早的 `0123` 可以离开保留范围。继续处理 `wxyz` 后，最近八字节又变成 `ABCDwxyz`。

<div class="zl-demo-mount"><zlib-demo kind="window"><p>处理位置从 8 前进到 12，再到 16。保留的最近八字节依次为 0123ABCD、ABCDABCD、ABCDwxyz；离开范围的旧字节不再用于之后的匹配。</p></zlib-demo></div>

图里的位置属于整条输入流。真实实现还要把这些字节放进有限的数组。`deflate` 使用一块连续字节区，先向后填充；接近末端时，把仍需保留的部分搬向数组开头，再使用腾出的空间。因而，“逻辑上保留最近的内容”与“每次前进都搬一次数组”是两回事。

### 实际 C 中的搬移 {#window-code}

读搬移代码之前，先说清它必须同步调整的几个位置。压缩器状态指针叫 `s`，`s->window` 表示其中的字节数组。字段 `strstart`、`match_start`、`block_start` 分别保存当前输入、暂存匹配和当前块起点在数组中的位置。局部量 `wsize` 是本次搬移要减去的字节数，`more` 是数组末端的空闲字节数。注释中的 `MAX_DIST` 是实现允许的最远回退搜索距离，在[窗口章节](/sample/window.html#positions)中展开。这些位置和距离都以字节为单位。

下面四条语句取自项目固定版本的 [`fill_window`](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/deflate.c#L287-L290)，位于需要搬移的分支内部：

```c
zmemcpy(s->window, s->window + wsize, (unsigned)wsize - more);
s->match_start -= wsize;
s->strstart    -= wsize; /* we now have strstart >= MAX_DIST */
s->block_start -= (long) wsize;
```

第一行用 `zmemcpy` 把仍有用的字节复制到较小下标。后三行从暂存匹配、当前处理点和当前块起点中，减去同一个搬移量。

可以用一个简单的算式理解：当前位置从 `800` 变成 `288`，候选位置从 `700` 变成 `188`，两者都减去 `512`，距离仍是 `100`。数组下标改变了，匹配指向的字节没有改变。

八字节窗口仅用于图示；真实 zlib 不接受这样的窗口配置。实际数组布局、搬移条件、最远搜索距离，以及位置表怎样同步更新，放在[滑动窗口章节](/sample/window.html)中逐项展开。

### 在保留范围里加快查找 {#window-search}

有了字节窗口，仍然可以在其中逐个尝试历史位置。但每次都从头找，会反复比较许多不可能匹配的字节。**哈希链解决的是第二个问题：怎样少检查一些候选。**

zlib 用片段开头的三个字节计算哈希，把可能匹配的位置归到同一个桶。`head` 记录桶里最近的位置，`prev` 把它接到更早的位置。它们保存的是查找线索，字节本身仍在窗口中。哈希相同只表示“值得检查”，真正的匹配长度还要逐字节比较。

看下面的历史和输入。最近的候选位置 `4` 开始于 `ABCR`，更早的位置 `0` 开始于 `ABCQ`。待处理输入是 `ABCQABCX`。

```text
位置   0    4    8
       ABCQ ABCR ABCQABCX
       ↑    ↑    ↑
       更早 最近 当前位置
```

只检查最近候选，会找到 `ABC`，长度为 `3`。再沿链检查一次，则可以找到 `ABCQABC`，长度为 `7`。两个候选都以相同的三个字节开始，后面的差异才决定最终匹配长度。

<div class="zl-demo-mount"><zlib-demo kind="search">
  <p>简化候选链中，预算 1 只检查最近候选，得到长度 3；预算 2 再检查更早候选，得到长度 7。它展示搜索预算的影响，不复现实际哈希函数。</p>
</zlib-demo></div>

如果链很长，继续搜索也有成本。zlib 的搜索设置包括最多检查多少候选，以及找到多长的匹配就可以提前停止。更高的压缩级别可以花更多时间寻找匹配，但它仍然是有边界的搜索，不保证找到全局最优的压缩表示。

窗口保存近期字节，哈希链帮助找到候选，字节比较确定长度，搜索预算限制所花的时间。这四件事合起来，才得到可以提交给编码器的匹配。下一节再说明：找到一个匹配后，为什么有时还值得等一步。

## 延迟匹配 {#lazy}

假设现在已经找到一个长度为 `3` 的匹配。立刻采用它，看起来很自然。但如果下一个位置能开始一个很长的匹配呢？

让历史里已经有这两段内容：`XABZ` 和 `ABCDEFGH`。当前输入是 `XABCDEFGQ`。

```text
历史：!XABZ!ABCDEFGH!
当前： XABCDEFGQ
       ↑ 当前位置
```

当前位置以 `X` 开始，可以匹配历史中的 `XAB`，然后在 `Z` 和 `C` 处停止，长度是 `3`。

向前看一个位置，当前后缀变成 `ABCDEFGQ`。它可以匹配历史中的 `ABCDEFG`，直到 `H` 与 `Q` 不同，长度是 `7`。

因此，我们可以先输出一个字面量 `X`，再采用从下一个位置开始的长匹配。这就是“延迟匹配”：暂缓对当前位置的决定，先看下一处有没有更长的匹配。

<div class="zl-lazy-comparison">
  <div><span>立即采用</span><b>XAB</b><i>CDEFGQ</i><small>先使用长度 3 的匹配</small></div>
  <div><span>多看一步</span><i>X</i><b>ABCDEFG</b><i>Q</i><small>先输出 X，再使用长度 7 的匹配</small></div>
</div>

zlib 的慢速策略保存上一个位置的匹配。若新位置找不到更长的匹配，就使用之前保存的那个；若新匹配更长，就把之前的首字节作为字面量输出，继续考虑新匹配。搜索条件还会限制何时值得做这一步。

这个例子比较的是可用匹配，并不声称第二条路径在所有编码条件下都有更小的最终比特数。长度、距离和字面量的编码成本不同；局部匹配选择与完整块的最小成本不是同一个问题。

## Huffman 树 {#huffman-tree}

我们已经减少了重复发送的字节，但符号本身仍要编码。如果每个符号都占相同的位数，常见的符号就没有得到任何优待。

先用四个抽象符号做一个实验。假设一个块中，`A` 出现 `8` 次，`B` 出现 `4` 次，`C` 和 `D` 各出现 `2` 次。固定用两个比特表示每个符号，总计需要 `32` 位。

我们希望常见的 `A` 更短，但还要能连续解码，不能依赖符号之间的分隔符。一种办法是使用前缀码：任何完整符号的编码，都不是另一个编码的开头。

Huffman 构造从出现次数最少的两个结点开始合并。这里先把 `C:2` 和 `D:2` 合并成权重 `4` 的结点，再把它与 `B:4` 合并成 `8`，最后与 `A:8` 合并成根。

```text
2 + 2 → 4
4 + 4 → 8
8 + 8 → 16
```

合并时形成的每一层，最终都对应一位编码。于是 `A` 深度为 `1`，`B` 为 `2`，`C`、`D` 为 `3`。数据部分的成本变成：

```text
8 × 1 + 4 × 2 + 2 × 3 + 2 × 3 = 28 位
```

这里的固定两位对照仅用于解释四符号编码，不是 DEFLATE 的固定编码表。DEFLATE 实际使用的字母表和码长规则更大，也更具体。

## 规范 Huffman 编码 {#canonical}

树还可以左右翻转，得到另一组同样长度的编码。如果压缩器和解压器各自选一棵树，它们怎么保证得到相同的比特模式？

DEFLATE 使用规范 Huffman 编码，也就是按码长和符号顺序确定码字的约定。双方约定：先按码长，再按符号顺序，连续分配编码。这样就不必发送整棵树，只要让解压器知道每个符号的码长。

对于 `A:1, B:2, C:3, D:3`，分配过程是：

```text
A →   0
B →  10
C → 110
D → 111
```

从 `0` 跳到 `10`，可以理解为先越过上一长度已经使用的码，再把编号左移一位，为更长的码腾出位置。相同长度的符号则直接使用连续编号。

<div class="zl-demo-mount"><zlib-demo kind="huffman">
  <p>码长 1、2、3、3 产生 0、10、110、111。改变码长，可以观察更短的码怎样占用更多编码空间，以及哪些分配根本无法构成前缀码。</p>
</zlib-demo></div>

树上长度为 `1` 的叶子占据一半空间，长度为 `2` 的占四分之一。把各符号的 `2⁻码长` 相加，得到 Kraft 和。等于 `1` 时空间恰好填满；大于 `1` 时，有些编码必然冲突。

这个条件也给解码器一个早期检查：长度描述不合理时，不必等到解数据才发现矛盾。实际 zlib 的接受规则还区分完整表、空表和某些单符号情况。它们会在解码章节中继续展开。

<details class="zl-deep"><summary>深入 · 动态块的码长描述</summary>
<p>DEFLATE 有一套字面量/长度字母表，以及一套距离字母表。字面量值直接对应字节；长度符号与额外位一起给出匹配长度；距离也通过符号与额外位表示。块结束是字面量/长度字母表中的专用符号。</p>
<p>动态块发送的是这两套编码的码长。连续的相同码长和零码长又能用重复符号表示，而这些重复符号还需要一套码长编码。因此，动态块的描述里存在三套相关编码。后续解码时，需要先还原码长，再构建数据符号表。</p>
<p>真实 DEFLATE Huffman 编码还有码长上限。无约束合并得到的树可能太深，zlib 需要调整码长计数，再重新分配长度。四符号例子没有触发这个过程；它只解释构造动机和 规范编号分配。</p>
</details>

## 块类型与编码成本 {#blocks}

刚才的四符号例子把数据成本从 `32` 位降到了 `28` 位。如果为了告诉接收者这套新编码，又额外发送超过四位的信息，最终就没有省下空间。

动态表不是免费的。它适合有足够数据来分摊描述成本的块；很小的块可能更适合使用双方已经知道的编码，或直接存放原始字节。

DEFLATE 因此提供三种块：

| 块形式 | 接收者怎样知道内容 | 主要成本 |
| --- | --- | --- |
| 原样存储（stored） | 按长度直接读取原始字节 | 字节对齐、长度及其反码、原文 |
| 固定编码（fixed） | 使用格式预先规定的 Huffman 码长 | 头部、符号和额外位 |
| 动态编码（dynamic） | 先还原块自己的码长，再解符号 | 头部、码长描述、符号和额外位 |

zlib 在刷新块时计算固定编码和动态编码的成本，再考虑能否采用原样存储形式。原始字节必须仍然可用，原样存储分支才有内容可以复制。策略参数也会影响选择。

因此，从输入到压缩流其实经过两次不同的选择：先决定用哪些字面量和匹配表示原文，再决定怎样编码这一块符号。下一章沿着相反方向走：接收者怎样把这些比特还原成原文。


## 位序与位缓冲 {#bit-order}

现在站到解压器这一侧。它连续接收字节，取出其中的位，再把它们还原成符号。

字节中的位按从低到高的位置依次使用。普通数值字段按最低有效位先行；Huffman 码则按码字的最高有效位先行。于是，同一串位用“到达顺序”和“整数写法”展示时，看起来会反过来。

以 C 的码 `110` 为例。先到达的 `1` 放在缓冲区第 0 位，第二个 `1` 放在第 1 位，最后的 `0` 放在第 2 位。若按通常的高位在左写出缓冲区数值，它就是 `011`。

<figure class="zl-bit-order">
  <div><span>到达先后</span><b>第 1 位 → 第 2 位 → 第 3 位</b></div>
  <div><span>收到的值</span><b>1 → 1 → 0</b></div>
  <div><span>放入的位置</span><b>第 0 位 → 第 1 位 → 第 2 位</b></div>
  <div><span>整数的通常写法</span><b>第 2 位 · 第 1 位 · 第 0 位 = 0 1 1</b></div>
  <figcaption>到达顺序没有改变。最先到达的一位保存在整数的最低位。</figcaption>
</figure>

理解这个区别后，位缓冲就没有那么神秘了。zlib 把缓冲区数值保存在 `hold` 中，用 `bits` 记录其中有多少位有效。补入字节时放在现有有效位之后；解释某个字段或码字时，从低位取走它需要的数量。

<details class="zl-deep"><summary>深入 · 编码表示与位流</summary>
<p>实现不需要把收到的字节逐个反转，再送给另一个解码器。它可以在建表时按反转后的码值安排表项，然后直接用 hold 的低位查表。普通长度、计数和 额外位等数值字段仍然按它们自己的规则解释。</p>
</details>

## 解码表 {#lookup}

每次读取一位、沿编码树走一条边，就能完成解码。但真实实现可以把前几步合并为一次数组访问：查看若干低位，直接查表。

仍然使用 A=`0`、B=`10`、C=`110`、D=`111`，并让根表查看两位。表只有四个槽：

| `hold` 的低两位（高位在左） | 结果 | 此次消耗 |
| --- | --- | --- |
| `00` | A | 1 位 |
| `01` | B | 2 位 |
| `10` | A | 1 位 |
| `11` | 子表 | 先消耗 2 位 |

为什么 A 占了两个槽？它的码只有一位。只要最低位是 `0`，第二位是 `0` 还是 `1` 都不影响 A 的含义。根表查看了两位，却只会消耗一位。

试着解码消息 `AD`。按码字顺序拼接，得到 `0 | 111`；按缓冲区整数的写法，则是 `1110`。此时根索引是 `10`，我们仍然得到 A。丢掉一位后，缓冲区剩下 `111`：根索引 `11` 指向子表，再用剩下的一位 `1` 得到 D。

<div class="zl-demo-mount"><zlib-demo kind="lookup">
  <p>教学消息 AD 的码位依次为 0、1、1、1。初始 hold=1110、bits=4。先以低两位 10 查到 A，只消耗一位；剩余 111 通过根表 11 和子表 1 解出 D。</p>
</zlib-demo></div>

这个过程把三个概念分开了：**查看多少位、实际消耗多少位、最终产生哪个符号。** 如果查到 A 后也丢掉两位，就会吞掉属于 D 的第一位，后面的解码自然错位。

C 和 D 需要子表，是因为根表的两位还不够区分它们。把根表加宽，可以减少子表访问，却会增加表空间。真实 `inflate_table` 会按码长分布构造根表和子表，而不是固定展开一棵完整的十五层树。

<details class="zl-deep"><summary>深入 · 预读与实际消费</summary>
<p>位缓冲可能包含后续符号的位，快速解码路径也可能预先读取字节。那些位已经进入缓冲区，不表示它们都属于当前符号。退出快速路径时，实现会把尚未使用的整字节退回输入游标，并保留不足一个字节的剩余位。观察输入游标、bits 和实际解出的符号时，要区分这种预读和真正的消费。</p>
</details>

## 用小缓冲区分批解压 {#stream}

前面的解码过程回答了“压缩字节怎样恢复原文”。应用还要解决一个很实际的问题：**原文可能很大，我们希望只准备一小块输出内存，取回一批结果就把它写入文件或交给下一步处理。**

这就是这里“流式”的意思：同一个解压任务可以分成多次调用。一次调用从当前输入位置继续解码，向提供的输出空间写入结果；空间用完时，函数返回，应用取走结果，再给它一块可写空间继续。无需先把全部解压结果放进一大块内存。

先只看解压方向：`inflate` 的**输入是压缩字节，输出是恢复后的原文字节**。输出缓冲区是应用提供的一块内存，不是压缩块，也不是整个解压结果。

<figure class="zl-purpose-flow"><div><small>输入 · 压缩字节</small><code>73 74 82 40 00</code><span>一个完整的无封装 DEFLATE 流</span></div><b aria-hidden="true">→</b><div><small>同一个 inflate 任务</small><strong>保留尚未完成的工作</strong><span>输出空间不够时返回</span></div><b aria-hidden="true">→</b><div><small>输出 · 原文字节</small><code>ABABA</code><code>BAB</code><span>按顺序拼起来得到 ABABABAB</span></div><figcaption>输入有 5 个压缩字节，完整结果有 8 个原文字节。每次只提供 5 个输出位置，仍能完成任务。</figcaption></figure>

### 一块五字节内存，两次取回结果 {#stream-batches}

第一轮输出 `ABABA`，把五个位置写满。应用先取走这五个字节，然后可以复用同一块内存，让第二轮写入 `BAB`。最终保存的结果是 `ABABA` 接上 `BAB`，也就是 `ABABABAB`。

图中先把压缩比特的解析省略，直接执行我们已经认识的指令：输出 `A`、输出 `B`，再回退两个字节、复制六次。第一轮中，前两个位置给了 `A`、`B`，只剩三个位置可供复制，因此还有三次复制要等下一轮完成。

### 继续执行需要保留的两类信息 {#stream-memory}

第一类是**工作进度**。例如“这条复制指令还差三个字节，距离仍是 2”。实现把这样的阶段叫作 `MATCH`。下一轮从剩下的工作继续，不再重新解释同一条指令。

第二类是**仍会被引用的字节**。第一轮结果被取走后，第二轮的输出数组可以被覆盖，但回引用还需要其中的 `B`、`A`。解压器把必要的后缀保存在自己的历史窗口里：先从保存的历史读出 `B`、`A`，再从本轮新输出读出第一个 `B`，得到 `BAB`。

这里的解压历史窗口与前面的压缩窗口分工不同：压缩窗口帮助**找到**重复，解压窗口帮助**执行已经收到的回引用**。它们都保留近期字节，却不是同一块内存。

实际调用也可能因为缺少输入而暂停，例如一个字段只到了半截。遇到这种情况要补充输入；输出空间用完则要提供空间。若输入没有增加、空间也没改变，反复调用不会凭空带来进展。完整输入、输出、错误返回和结束协议见[暂停与调用接续章节](/sample/stream-state.html)。

# 实现需要保持的关系 {#verifying-zlib}

<p class="zl-part-intro">现在我们知道程序想做什么。接下来的问题是：每一步凭什么成立？</p>

前半篇让我们沿着一个输入走完了算法。但程序必须处理的还有另一种输入、更小的输出缓冲区、一次失败的分配，以及调用者允许的各种操作顺序。

形式化验证要把这些变化放进同一个精确的问题里。我们先从最小的一次写入开始，再看它怎样扩展到表、缓冲区和整个流的生命周期。

## 执行与循环不变量 {#write-proof}

回到长度为 6、距离为 2 的匹配。循环已复制了 `i` 个字节，现在准备写下一个。我们不能只知道最终输出应该是 `ABABABAB`，还要知道当前写入位置属于一块活的、可写的内存。

先把问题缩到一条算术关系。`length` 是这个示意循环总共要复制的字节数，`i` 是已经复制的字节数，`capacity` 是从目标起点开始可写的字节位置数；下一次写入使用下标 `i`。若 `i < length`，且 `length ≤ capacity`，那么 `i < capacity`。它在 Lean 里可以写成下面这样，其中 `Nat` 表示非负整数：

```lean
theorem next_write_in_bounds (i length capacity : Nat)
    (running : i < length) (room : length ≤ capacity) :
    i < capacity :=
  Nat.lt_of_lt_of_le running room
```

这里，`running` 和 `room` 是两个已有结论。证明项把它们接起来，得到写入索引的上界。Lean 内核检查这一步推理。

但真正的 C 程序并没有一个叫“自然数容量”的抽象对象。它有指针、数组、机器整数和堆。因此还要证明：这个 `capacity` 就是实际目标对象的有效范围，目标仍然活着，而且允许写入。输入的读取位置也需要自己的依据。

功能正确性还多问一步：写进去的值对不对？在这个匹配中，已经写出的字节要与独立定义的回引用语义一致。若源位置进入刚刚产生的输出，下一步读取到的也应是正确的字节。

把这些事实留在循环每次重新开始的位置，就是循环不变量。它记录已完成的工作，也准备好下一步的条件：前 `i` 个字节正确，当前读写仍然合法，剩余长度准确。执行一步后，证明同样的事实对 `i + 1` 成立。

<details class="zl-deep"><summary>深入 · 访问界与终止</summary>
<p>一个循环可以一直在数组范围内运行，却永远不退出。复制循环可以用剩余长度递减来论证终止；主解码循环还包含不消耗输入、也不产生输出的模式转换。这些静默步骤需要额外的控制秩，不能只数输入字节。</p>
<p>项目运行时给循环设置了有限的执行步数预算，源码中称为 fuel。证明还要排除实际步数预算耗尽，而不只是说数学上的循环最终会结束。终止和无泄漏都属于项目的安全目标，虽然它们本身并不是 C 未定义行为。</p>
</details>

## 表项的安全性与语义 {#table-proof}

前面的编码例子中，`C` 的编码是 `110`。根表先查低两位，再由子表选中 `C`。

现在只改一件事：把那个子表项的结果从 `C` 写成 `D`。索引不变，码长不变，所有访问仍然留在数组里。解码器却输出了错误的字节。

<div class="zl-demo-mount"><zlib-demo kind="table-proof">
  <p>保持相同的根表链接和子表索引，只把 C 对应表项的值改为 D。访问仍然有界；输入 110 的结果从 C 变成 D，因而不再符合规范编码。</p>
</zlib-demo></div>

所以“表安全”和“表正确”需要两条论证。前者说明即将读取的槽位已经初始化，索引有界，链接指向合法子表。后者说明槽位中的内容正好实现对应的编码：该输出字面量时输出正确字面量，该报告无效码时也不能冒充成功。

这两条结果必须说的是同一张表。证明某个数学函数能够生成正确的表，还不能说明翻译后的 `inflate_table` 确实把那些内容写进了堆。

生产者和消费者之间需要一座桥：构造器的实际执行建立表项关系，解码器的实际指针指向那些表项，查找证明再使用这个关系。详见项目的 [解码表论证](/reference/docs/proof/inftrees.zh.html)。

<details class="zl-deep"><summary>深入 · 表项的初始化覆盖</summary>
<p>根表的一个短码会复制到多个槽位。长码又需要子表。要允许解码器读取任意一个合法索引，构造证明必须覆盖所有可能到达的槽位，而不只是说明每次写入都没有越界。</p>
<p>空表和允许的单符号不完整表也需要单独解释。不能把它们当成完整前缀码，再直接套用“每个输入前缀都落在一个有效叶子下”的结论。</p>
</details>

## 共享缓冲区与前缀界 {#overlay}

压缩器里有一种更隐蔽的风险。待编码的符号和待输出的压缩字节可以共用内存。符号被读取后不再需要，腾出的空间就能容纳输出。

一个看似合理的证明目标是：最终压缩结果小于缓冲区容量。

先试试这个条件够不够。下面把内存缩成 32 个格子，符号从偏移 8 开始，每个占 3 格。在每一步，先读一个符号，再写它产生的输出。让安全计划与前重计划并排运行，只执行第一步。

<div class="zl-demo-mount"><zlib-demo kind="overlay">
  <p>前缀越界的教学计划中，初始已有 2 个输出字节。读完第一个符号后，未读符号从偏移 11 开始；若此时再写 12 个字节，输出会达到偏移 14，覆盖 11、12、13。最终输出只有 20 字节，小于容量 32，仍然无法修复早先的损坏。</p>
</zlib-demo></div>

最后一个数字虽然放得下，第一个危险前缀已经破坏了未来的输入。这是两种不同的条件。

这组小尺寸和写入计划专门用来展示区别，不是 zlib 可以产生这种块的证据，也不是漏洞复现。

实际共享符号分支中，配置计数 `lit_bufsize` 决定存储规模。把这个计数简记为 `B`，分配的待输出存储共 `4B` 字节，符号从偏移 `B` 开始，每个占 3 字节。读完前 `q` 个符号后，未读符号的起点向前移到：

```text
R(q) = B + 3q
```

这里 `q` 计数已经读取的符号，而 `R(q)` 是字节偏移。代入小图的 `B=8`、`q=1`，就得到 `R(1)=11`。再用 `K` 表示符号总数，`P(q)` 表示读完 `q` 个符号时已经写出的输出字节数。只知道最后的 `P(K) ≤ 4B`，就像只看动画的最后一帧。逐符号发射需要控制沿途的 `P(q)`。项目采用的充分界形如：

```text
P(q) < R(q)       对相应的逐符号发射边界
```

还要证明每次中间写入都不碰到未读后缀。第一个符号被读取前的树描述和头部写入、最后的结束码和位对齐，又各有自己的空间条件。

<details class="zl-deep"><summary>深入 · 严格界与实际重叠</summary>
<p>若已写输出表示为半开区间 <code>[0, P)</code>，未读区间从 <code>R</code> 开始，那么 <code>P = R</code> 本身还没有重叠。项目这里使用严格不等式作为足够的空间界。不要把这个证明条件的失败，自动画成一次已经发生的非法写入。</p>
<p>动画应按实际写入触及的格子标记损坏。数学预算的边界和程序真正写坏了什么，要分开显示。</p>
</details>

## Huffman 频率界 {#huffman-bound}

固定编码下，每个符号的成本有直接上界，因而可以累计出一个保守的输出预算。动态编码的困难在于：早期符号可以很长，后面的常见符号却很短。

于是，“整个动态块比固定块短”依然只是总量信息。它不能单独限制早期输出。码长满足 Kraft 条件，也只说明它们构成一种合法编码，没说明它们与这个块的符号频率有什么关系。

真正有用的事实来自实际 Huffman 构造。树不断选择权重较小的节点进行合并。要让某个叶子处于很深的位置，周围必须有足够的合并结构和权重。这种深度与频率的关系，能够帮助限制长编码对前缀成本的贡献。这里的“前缀成本”，是读完前几个符号时已经产生的比特数；它决定输出会不会提前追上尚未读取的符号。

项目的一条数学路线利用 Fibonacci（斐波那契）式的权重增长：树越深，周围需要的合并权重越大。随后还要分析码长超过格式上限时的修复。它最终要提供前缀预算，保护未读符号。

但数学预算的输入不能凭空给出。还需要从真实符号统计、队列选择、合并和长度修复中导出它的前提，再连接到实际位缓冲和写入操作。这里最重要的工作往往就是这些连接，而不是给一个抽象树再证明一次性质。

具体推导见 [共享缓冲区论证](/reference/docs/proof/trees.zh.html#the-overlay-lemma-f9)。当前完成范围统一由[进度记录](/reference/docs/progress.zh.html)维护。

## 跨调用不变量 {#history-proof}

前半篇的解压例子在 `ABABA` 后暂停。还有三个字节没复制，距离仍然是 2。下一次调用换了一块输出缓冲区，程序应该接着工作。

这时，正确的输出前缀并不等于“旧输出指针永远有效”。调用者可以更换缓冲区，程序自己的历史窗口则负责保留后续操作所需的字节。证明需要追踪的是逻辑历史与当前实际存储之间的关系。

一个调用返回时，要留下下一次调用能够使用的表示不变量。它既包含内存事实，也包含算法事实：流拥有的块仍然活着，表和窗口指针有合法来源，已经消费的输入与已经产生的输出对应，未完成匹配保存了准确的剩余工作。

这个关系从哪里来？初始化必须先建立它。之后，每个允许的操作维持它，或产生接口规定的结束状态。仅仅写出一个看起来强大的不变量，并假设所有调用从它开始，并不能说明真实调用会到达这种状态。

调用辅助函数也一样。先证明翻译后的辅助函数满足自己的规格，再由调用者从当前状态建立它的前提。不能直接把“辅助函数正确”当作未经证明的假设。

<details class="zl-deep"><summary>深入 · 局部证明的组合前提</summary>
<p>一个引理可能给出堆中的游标范围，另一个引理却需要函数局部寄存器中的当前游标。执行期间两者不一定相等：程序可能先把字段加载到局部变量，最后才写回。连接证明必须在正确的执行点上说明它们的关系。</p>
<p>同样，某个分支证明的前提可能由普通数据调用维持，却被重置、设置字典、复制或恢复操作改变。整个调用序列的结论要覆盖接口允许的这些转换，不能只把最常见的数据路径重复很多次。</p>
</details>

## 所有权与失败清理 {#ownership}

成功路径把状态交给下一次调用。失败路径也必须交代它留下了什么。

考虑一个只有两项资源的教学初始化：先分配控制记录 `state`，再分配保存历史字节的数组 `window`。第二次分配失败时，第一块内存已经存在。直接返回错误仍然可能泄漏它。

<div class="zl-demo-mount"><zlib-demo kind="ownership">
  <p>教学模型先分配 state，再分配 window。若 window 分配失败，先释放已经拥有的 state，再返回错误。若初始化成功，两项资源继续归流所有，直到 end 释放。真实 API 需要按各自的实际分配顺序论证。</p>
</zlib-demo></div>

成功初始化不应该让堆恢复原样。它应该获得资源，并清楚地保有所有权。失败清理和正常结束则要释放它们，而且恰好释放一次。

动画里还有一组始终不动的“其他对象”。它们代表调用者原本拥有、这次操作无权修改的内存。证明这些对象保持不变，就是对无关存储的保持条件，证明中通常称为 frame 条件。只数最终还剩多少块内存，不足以说明程序没改坏别人的数据。

真实生命周期还包含复制和部分失败：复制操作获得独立的目标存储，内部指针需要重定位；复制失败要清理本次获得的资源，并保留原来的流。错误返回的内存效果要按分支写清楚。

## 验证范围与信任边界 {#trust}

到这里，我们一直在讨论“执行”和“证明”。zlib-f 中被 Lean 内核检查的，是关于 Lean 计算的命题。这个计算是选定 C 源码的逐语句翻译，在项目运行时定义的堆、指针、算术和循环语义下执行。

因此有两条连接需要独立审查：翻译是否忠实于选定的 C，运行时是否足以表示相关的 C 行为。内核会检查推理，没有自动检查这两条连接。

<div class="zl-proof-chain" aria-label="从真实源码到结论的连接"><span>选定的 C</span><i>翻译与语义审查</i><span>Lean 中的执行</span><i>内核检查证明</i><span>独立规格</span></div>

这个区别会产生具体义务。例如，模型中的新指针字段默认为 NULL。遗漏一次初始化写入后，读取该字段再与 NULL 比较，可能没有触发模型故障。因此还要证明：真实程序的相应指针字段在被读取前已经写过。

模型中的新整数单元则具有任意值，定理必须对所有这些值成立。重复读取一个未初始化单元在模型里得到相同值；论证不能依赖这种一致性来替代对更一般 C 行为的说明。对象堆也不提供完整的机器地址和 ABI 字节布局。边界详见 [信任边界](/reference/docs/trusted-base.zh.html)。

差分测试能发现真实 C 和翻译之间的行为偏差，提供忠实性的证据。证明变异测试则修改翻译，检查相应函数的证明是否失败。审计还检查公理、登记和其他接受要求。它们各自补充一种证据，不互相替代。

本文的交互运行独立编写的教学模型。它们让某一次执行可见，不运行 Lean 证明，也不执行 zlib 的 C 翻译。针对全部允许输入的结论，需要回到精确的命题和对应证明。

zlib-f 的首个目标是默认 x86_64 Linux/LP64 静态构建和默认分配器。畸形输入、错误返回和分配失败仍在需要覆盖的范围内。完整验证未完成。当前结果、阻塞项和剩余工作统一见 [项目进度](/reference/docs/progress.zh.html)，接受结论需要查看具名提交上的证据与 CI。
