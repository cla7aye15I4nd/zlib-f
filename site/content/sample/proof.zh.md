[块编码](/sample/blocks.html)、[位写入](/sample/bits.html)和[共享存储](/sample/storage.html)追踪了同一次转换：选定的 `A`、`B`、长度 6／距离 2 展开为 `ABABABAB`，最终固定编码占 38 个有效位，对齐后为 `73 74 82 40 00`。现在要让这些步骤的保证在交接时仍然成立，而不是分别描述互不相干的输入和输出。

需要同时保持三件事：记录及比特表达原来的输入，写出字节时不破坏未读记录，输出空间耗尽后能继续交付同一个后缀。把五个字节分成两次交付，是检查最后一条的具体例子：第一次给出 `73 74` 后，状态必须记住剩下的是 `82 40 00`，不能重新编码或跳过其中一部分。

| 应有的保证 | 例子中检查什么 | 可能怎样出错 |
| --- | --- | --- |
| 保持输入含义 | 距离 2 的复制逐字节恢复余下的 `ABABAB` | 记录的长度偏移或距离错一位 |
| 精确编码 | 六个字段连续形成 38 位 | 跨寄存器时漏位、重复位或插入填充 |
| 保持未读输入 | 先读完 B 的记录，再复用其位置 | 待交付写入提前覆盖匹配记录 |
| 精确交付并继续 | 五字节可以分成 2 字节与 3 字节交付 | 返回后从错误游标继续，重复或漏字节 |

下面沿记录含义、比特追加、未读存储和字节交付建立连接。完整块与公开调用序列的组合证明尚未完成；需要把局部定理的寄存器条件、容量条件和输入关系建立在每次实际返回状态上。

```mermaid
flowchart LR
    Input["已接受的输入字节"] -->|"匹配与符号记录"| Symbols["字面量 / 匹配记录"]
    Symbols -->|"块编码"| Bits["DEFLATE 比特"]
    Bits -->|"位写入器"| Pending["待交付字节与缓冲位"]
    Pending -->|"交付"| Output["调用者输出"]
    Storage["保持未读记录"] --> Symbols
    Storage --> Pending
```

## 符号的含义 {#meaning}

先回到第一个输出比特产生之前。字面量展开成它自己。匹配则从已经展开的历史里逐字节读取；读取距离不变，历史却会随着写入增长。因此，例子中距离只有 2 的匹配，仍然可以产生 6 个字节。

压缩器需要把这种展开与已经接受的输入联系起来。提交一个字面量后，符号展开多出同一个字节。提交一个匹配后，展开多出的那段内容，要由此前的匹配搜索给出字节相等的依据。延迟匹配中的暂存决策也要进入这个记账：把输入接收到 **预读区**（`lookahead`，已经缓冲、尚未作出匹配决策的输入），与最终提交一个符号，是两个不同的时刻，不能把它们的游标混为一谈。

接下来才把逻辑符号连接到实际记录。存下的三个字节必须能还原相同的距离，以及字面量或长度偏移；频率更新也必须统计这个符号。现有的 [`tr_tally_spec`](/reference/source/ZlibF/Proof/trees.c.tally.html#L327) 在明确的空间和符号取值前提下，描述翻译后的符号记录究竟写了什么。它本身没有证明此前搜索选中的字节与输入相同。连接的这一段属于调用者。

发射时，读出的同一条记录要变成格式要求的编码和额外位。固定编码与动态编码使用不同的编码表；原样存储走另一条分支，直接复制原始字节。这些分支使用不同的中间表示，但最终可以满足同一个独立解码关系。[`Deflate.Valid`](/reference/source/ZlibF/Spec/Format/Deflate.html#L160) 通过解码定义无封装格式的目标，成功的含义因此不取决于“压缩器碰巧写出了什么”。

## 精确的比特输出 {#bitstream}

先看跨界发送 B 的那一步：调用前，待交付字节区为空，寄存器的 11 位代表块头和 A；调用后，`73 74` 的 16 位已成为待交付字节，剩余 3 位在寄存器。两边都必须表示原来的 11 位后接 B 的 8 位，即同样的 19 位。这个等式说明我们为何需要同时描述数组和寄存器。

位写入器把抽象比特落到实际状态里。一些完整字节已经在 `pending_buf` 中，随后几位还在 `bi_buf` 中。这里 `pending` 是已缓冲完整字节的数量，`bi_buf` 保存后续暂存位，`bi_valid` 记录这些位的个数。把同时涵盖这两个位置的逻辑位序列叫作 `outBits`：

```text
outBits = byte_bits(pending_buf[0 .. pending))
          ++ low_bits(bi_buf, bi_valid)
```

这里的式子用于待交付字节区从缓冲区基址开始的局部发射状态。`byte_bits` 按最低位在先展开每个字节；`++` 表示先后拼接；`low_bits(x,n)` 只取 x 的低 n 位，按最低位在先排列。部分交付以后，尚未交付的区间要从实际 `pending_out` 游标读取，最后一节会把这个游标接入全局关系。

每个字节按低位在先展开。存储的 Huffman 码字则已经为这个写入器反转过。于是，一次 `send_bits` 最有用的结论是：返回后的序列，恰好等于旧序列后接这次要求发送的字段。比特从寄存字段移到字节数组，并不会改变它们的顺序。

定理中的 `TreesInvAt` 给一组具体的状态条件起了名字：状态和字节数组确实存在于当前堆中；待交付字节与符号记录的指针指向同一个可写分配的规定位置；树描述符指向相应数组；有效位数在 0 到 16 之间；缓冲区没有越过有效位的杂位；符号游标处在三字节记录边界内。它没有替调用者提供“本次追加仍有空间”或“未读记录不会被覆盖”的结论，那些需要另行建立。

实际的 [`send_bits_spec`](/reference/source/ZlibF/Proof/trees.c.bits.html#L411) 分别处理“留在缓冲区”和“写出一个 16 位字、保留余位”两条分支。当前命题明确要求 `TreesInvAt`、0 到 15 之间的发送长度、能装入该长度的值，以及足够的比特空间。它给出实际无故障执行、返回堆上的同一不变量、精确追加的比特，并保证写入区间之外的字节不变。

这种局部结论可以交给下一次调用。[`EmitState.step`](/reference/source/ZlibF/Proof/trees.c.emit-state.html#L34) 把实际发射组合起来：先追加 `u`，再追加 `v`，就得到 `u ++ v`。它同时传递返回堆和保持不变的字段，而不只传递一个比特等式。调用者使用的是辅助函数已经证明的执行结果，并在调用点建立它的前提；不能把“辅助函数遵守契约”直接当作未经证明的假设。

## 未读存储的保持 {#prefix}

比特正确，还不足以说明剩余符号能够继续编码。写入器可能刚刚追加了正确字段，却破坏了下一轮需要读取的记录。

这里要比较同一共享分配内的两个字节偏移。`B` 是布局尺度，在状态中叫 `lit_bufsize`，也就是第一条记录的起点偏移。设 `q` 为已经完整读出的记录数，每条占三字节，因此下一条未读记录从 `R(q) = B + 3q` 开始。设 `P(q)` 为这些记录发射后，下一个空闲输出字节相对同一分配基址的偏移。证明必须让每次实际写入都避开未读后缀。项目采用的一个方便的充分边界是 `P(q) < R(q)`，并同时要求中间写入保持未读内容。边界恰好相等本身并不意味着发生覆盖；是否重叠，要看具体的半开写入区间。

回想上一章人为构造的前期集中写入方案。`B = 8` 时，读完第一条记录，未读起点变成 11。原本已有两个待交付字节，再写十二个字节后，下一个空闲位置变成 14。写入区间 `[2,14)` 与未读存储相交于 `[11,14)`。最终的 20 字节虽然装得进 32 字节的分配块，却无法恢复这三个字节。这说明归纳需要检查每个前缀，不能只检查最后一个。

固定编码块的数量关系比较直接：一个字面量至多 9 位，一个匹配至多 31 位。假设进入时没有待交付字节，且已有缓冲位至多 7 位。把三位块头和写入器的字节上界合起来，得到相应发射前缀的一个保守估计：

```text
P(q) ≤ (7 + 3 + 31q) / 8 + 1
```

先统一单位。分子是位数：入口至多 7 位、块头 3 位、q 条记录至多 `31q` 位。除以 8 转换成字节；额外的 1 为暂存与取整留出保守余量。这里用有理数上界估计整数的字节数。

再比较两条边界的增长速度。每读完一条记录，读取边界前进 3 字节；输出的最坏预算却是 `31/8` 字节，多出 `31/8 - 3 = 7/8` 字节。q 条记录总共可能多用 `(7/8)q` 字节，入口还需 `10/8 + 1 = 9/4` 字节。只要初始间隔 B 能容纳这两项，即 `(7/8)q + 9/4 < B`，两条边界就仍然分开。

最后使用记录上限 `q ≤ B−1`。代入后，左边至多为 `7B/8 + 11/8`，因此 `B > 11` 足够；实际共享布局允许的最小 B 是 128。这个计算给出了充足间隔。把它接到程序时，还需要证明本次发射确实满足“入口无待交付字节、暂存位至多 7 位”等条件，并分别处理记录 0 之前的块头、各次中间写入、块结束标记和最终对齐。[完整的 F9 论证](/reference/docs/proof/trees.html#the-overlay-lemma-f9) 保留了这些具体义务。

## 动态编码的前缀成本 {#dynamic}

动态编码块在第一条记录之前，还要先发送树的描述。较早的符号也可能恰好使用长码。选择动态编码，是因为它完整的舍入成本优于固定编码；这个比较限制了总量，却没有限制昂贵的符号出现在什么位置。

需要的预算因此包含树描述，以及每个符号前缀的成本。仅靠 Kraft 不等式还不够。Kraft 描述合法的编码空间，而这里需要把码长与构造这棵树时实际使用的频率联系起来。

这里需要回到[树构造](/sample/huffman-tree.html#queue)实际选择了什么：队列怎样选取较轻节点，合并怎样累加频率，深度怎样打破平局，以及[长度修复](/sample/huffman-lengths.html#repair)怎样改变分配。前缀成本界必须使用这棵实际构造树的频率与码长关系，再计入规范码字、额外位和写入器的舍入。机器整数求和不溢出、节点深度没有截断，也是把数学估计用于实际执行的前提。[树构造与码长修复论证](/reference/docs/proof/trees.html#length-repair-f8)给出所需记账。

## 交付与调用边界 {#composition}

交付时，`len` 是内部待交付字节数 `s->pending` 与调用者可写字节数 `strm->avail_out` 的较小值。内部读取游标为 `s->pending_out`，调用者写入游标为 `strm->next_out`，`total_out` 统计此前累计交付的字节数。这里可直接跟随 [`flush_pending` 的交付核心，deflate.c:978–983](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/deflate.c#L969-L986)：

```c
zmemcpy(strm->next_out, s->pending_out, len);
strm->next_out  += len;
s->pending_out  += len;
strm->total_out += len;
strm->avail_out -= len;
s->pending      -= len;
```

第一行从尚未交付的起点复制 `len` 个字节。第二、三行让调用者的写入位置和内部读取位置前进相同的量。第四行把这次交付加入累计输出；第五行扣除调用者空间；第六行扣除未交付字节。`len` 在前面的源码中取两边可用量的较小值，归零时另有游标复位。

对五字节例子，若调用者只能接收两字节，第一次复制 `73 74`，待交付从 5 变成 3，内部游标前进 2。下一次从该游标复制 `82 40 00`，而不是重新从分配起点复制。证明要同时保持这个字节等式、两边范围的合法性以及复制的分离条件。

这段复制移动的是已经编码好的一个前缀；它不应凭空产生字节，也不能丢掉尚未交付的后缀。输出空间有限时，一段交付可能跨越多次调用。因此，返回边界既需要字节记账，也需要保留编码器剩余的状态。

一个有用的关系，把累计交付给调用者的字节、当前待交付区域和缓冲位，连接到逻辑符号已经编码出的前缀。输出耗尽时，它解释已经交付了什么、还剩什么。恢复执行时，证明从这个实际返回状态继续。前一个块的字节尚未交付完毕时，不能直接给新块套上“初始待交付字节区为空”的前提。

这样，记录、寄存器、内部字节和调用者输出都在解释同一次压缩：`ABABABAB` 的三条选定记录，成为五个 raw DEFLATE 字节；分批交付后，接收者仍会得到 `73 74 82 40 00`。沿[解压与解码](/verification/decoding.html)可以继续看它们怎样变回八个原始字节。

完整流还需要封装头尾、刷新、初始化和清理。[流式状态与封装](/verification/streaming.html)说明这些步骤为何围绕同一个块过程发生；公开 [`deflate` 契约](/reference/functions/deflate.html)及 [`deflate_sequence` 目标](/reference/targets.html#deflate_sequence)规定跨调用的完整保证。这些层次的完整组合证明尚未完成，具体连接见 [deflate 实现论证](/reference/docs/proof/deflate.html)与[项目进度](/reference/docs/progress.html)。
