第二次遇到 `ABCD` 时，压缩器可以发出“向后四字节，复制四字节”，省去重复写出这四个字节。要找到这条引用，它必须还记得第一次的 `ABCD`。但输入可以一直增长，内存不能跟着增长。因此压缩器只保留近期历史，让太旧的字节退出搜索范围。

先看一个只保留最近八字节的教学例子。已经处理 `0123ABCD` 后，八字节全在历史中；再处理 `ABCD` 后，最近八字节变成 `ABCDABCD`；再处理 `wxyz` 后，变成 `ABCDwxyz`。第二组 `ABCD` 可以引用第一组；当 `0123` 离开保留范围，就不能再拿它作新的引用来源。

<div class="zl-demo-mount"><zlib-demo kind="window"><p>依次处理到第8、12、16字节：最近八字节由 0123ABCD 变成 ABCDABCD，再变成 ABCDwxyz。保留范围向前走，容量始终为八字节。</p></zlib-demo></div>

这里的八只是解释逻辑保留范围，不是 zlib 的合法窗口配置，也没有画出它的物理搬移时机。DEFLATE 的距离最多为 32768；本实现搜索时还要预留比较空间，实际搜索界稍小。下面会把这两层分开。

窗口这一步接收调用者的新字节和压缩器的旧状态，产物是**仍可搜索的历史、连续的待处理字节，以及与它们一致的位置索引**。它还没有生成压缩符号。下一篇[候选搜索](/sample/match-search.html)才决定用字面量还是引用；[匹配证明](/sample/match-proof.html)解释这些交接如何保持字节含义。

## 从保留范围到实际数组 {#layout}

一个直观实现可以每来一个字节就删掉最老字节、搬动其余内容。zlib 避免这种频繁搬移：它在更大的连续数组里向前处理，接近末端时才成批搬动。于是同一个字节既有永不改变的逻辑流位置，也有会在搬移后改变的数组下标。近期历史的逻辑范围，并不等于整个物理数组。

## 位置与保留字节 {#positions}

现在给这张存储图命名。`W = w_size` 是配置的窗口尺度，普通布局的 `window` 数组实际分配 `2W` 个字节。它同时容纳历史和待处理输入；“分配了 `2W`”不表示“可以回引 `2W` 字节”。`strstart` 是当前处理位置的数组下标；`lookahead` 表示从这里开始，已有多少真实输入字节可用。因此，真实数据结束于 `strstart + lookahead`，不能超过 `2W`。

```text
窗口偏移：0                         strstart       strstart+lookahead        2W
          [ 保留的较早字节 .........][ 尚未处理的输入 ][ 空闲区 ..............)
```

字节窗口不是按 W 取模寻址的环形数组。字节比较直接使用 `2W` 数组中的连续位置；循环复用的部分在后面的前驱表中。处理接近数组末端时，保留字节向低地址搬动，释放出的区域才能继续装入新输入。

几个常量说明了实现为什么预留空间。`MIN_MATCH` 为 3，`MAX_MATCH` 为 258，而 `MIN_LOOKAHEAD = MAX_MATCH + MIN_MATCH + 1 = 262`。这个压缩器的 `MAX_DIST` 是 `W - 262`；通常 W 为 32768，因此搜索距离上限为 32506。这是实现的搜索限制，不是在把 DEFLATE 格式允许的距离上限 32768 改写成另一个值。数组里即使还放着更早的字节，它们也可能已经超出当前允许的搜索范围；物理上未被覆盖，不等于逻辑上仍可回引。

选定默认构建的参数归一化给出 `512 ≤ W ≤ 32768`。对于 zlib 封装压缩，允许的 `windowBits = 8` 会被归一化为 9；raw 与 gzip 的参数校验则拒绝这个八位窗口情形。因此 W 不会成为 256。这个区别很重要：256 减去预留的 262，无法得到可用的正距离界。精确参数范围见 [deflateInit2_](/reference/functions/deflateInit2_.html)。

## 补充输入与预读区 {#refill}

策略需要更多输入时，`fill_window` 先计算真实数据之后还有多少空间：

```text
more = window_size - lookahead - strstart
```

这是实际读取发生的位置，摘自固定版本 [`fill_window`，311–312 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/deflate.c#L311-L312)，不是教学伪代码：

```c
n = read_buf(s->strm, s->window + s->strstart + s->lookahead, more);
s->lookahead += n;
```

第一行把目的地址放在已有真实数据之后，并把空闲量 `more` 交给 `read_buf` 作读取上限。第二行只增加实际读到的 `n`，而不是增加请求量。这样在输入不足时，计数仍描述真实存在的字节。

完成必要的滑动后，`read_buf` 把至多 `min(avail_in, more)` 个字节复制到 `window + strstart + lookahead`。它推进调用者输入指针，减少 `avail_in`，更新输入记账及选定封装的校验和，再把 `lookahead` 增加相应数量。接收这些字节，并不表示匹配策略已经把它们消费成符号。

只要调用者仍有可用输入，循环就尽量取得 262 个字节的预读区。到了策略层，`Z_NO_FLUSH` 下预读不足时可以返回 `need_more`，而不是立刻对一个短前缀作出决定。结束或刷新调用则可以处理不足这个长度的尾部。这些内部结果不是公开 `deflate` 的返回码，外围协议见[调用接口](/sample/interfaces.html)。

真实数据之后，还可能有一段已经初始化的尾部。`high_water` 记录窗口写到过哪里。补充输入后，若尚未初始化，zlib 会把当前数据末尾之后至多 `WIN_INIT = 258` 个字节清零，并把范围截在分配边界之内。这为比较例程较宽的扫描范围提供初始化内容。但这些零不会变成输入：限制一个匹配能消费多少真实字节的是 `lookahead`，不是 `high_water`。

补充输入还会完成延期的哈希插入。如果上次调用结束时只剩一或两个字节，这些位置还没有完整的三字节字符串可供插入。`insert` 计数保存这部分工作。新字节到达后，`fill_window` 重新准备滚动哈希，把现在已经完整的字符串插入，再继续普通搜索。

## 带具体偏移的滑动 {#sliding}

滑动条件是 `strstart ≥ W + MAX_DIST`，也就是 `strstart ≥ 2W - 262`。取合法的 W=512，令 `strstart = 800`、`lookahead = 100`。真实数据结束于 900，剩余空间 `more = 1024 - 900 = 124`。滑动阈值为 762，因此进入滑动分支。

它复制 `W - more = 388` 个字节，把 `[512, 900)` 搬到 `[0, 388)`。这里搬的是上半区已经有效的部分，不是无条件复制全部 512 个字节。源、目标区间互不重叠。`strstart` 减去 512，变成 288；`lookahead` 仍为 100。空闲空间增加到 636 个字节。若还有 300 个新字节，下一次读取便把它们放进 `[388, 688)`，令预读量达到 400。

| 量 | 滑动前 | 滑动后 | 再读取 300 字节后 |
| --- | --- | --- | --- |
| `strstart` | 800 | 288 | 288 |
| `lookahead` | 100 | 100 | 400 |
| 真实数据末尾 | 900 | 388 | 688 |
| 空闲空间 | 124 | 636 | 336 |

原来位于 700 的保留候选变成 188。它与当前位置的距离仍是 `800 - 700 = 288 - 188 = 100`。在逻辑层面，窗口偏移 0 代表的输入流基准已经前移 512，所以两组下标仍然指向同一批流字节。

把例子接回实际实现：固定版本 [`fill_window`，287–290 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/deflate.c#L287-L290)的连续四行是：

```c
zmemcpy(s->window, s->window + wsize, (unsigned)wsize - more);
s->match_start -= wsize;
s->strstart    -= wsize; /* we now have strstart >= MAX_DIST */
s->block_start -= (long) wsize;
```

第一行真正搬动字节：目的地是数组开头，来源是偏移 W，长度正是例子的 388。第二行平移保存的匹配位置；这不保证该字段此时一定是有效候选。第三行平移当前处理位置。第四行用有符号运算平移块起点，以容许它落到当前数组之前。后续源码还会限制延期插入量、调用 `slide_hash`，并把新增的 W 字节加入空闲计数。

元数据也必须完成相同的变换。`slide_hash` 对每个位置 m 执行：若 `m ≥ W`，保存 `m-W`；否则保存零哨兵。头表和前驱表都需要更新。`block_start` 是有符号量，滑动后可以为负：原始块的开头可能已经离开窗口。因此，[stored 块选择](/sample/blocks.html#selection)还必须判断原始字节指针是否可用。旧的 `match_start` 也可能只是暂存的过时值；它的无符号减法需要在真正使用该字段的位置分析，不能把它永久当成有效引用。

## 滚动哈希与前驱槽位 {#hash}

逐一搜索所有较早位置，会重复比较很多不可能匹配的候选。zlib 用短哈希给三字节字符串建立索引：把这三个字节算成一个较小的整数，作为桶号。相同的三字节串一定落入同一桶，不同的串也可能落入同一桶，所以桶里存的是待检查的候选，而不是已经确认的匹配。默认 `memLevel = 8` 时，`hash_bits = 15`、`hash_size = 32768`、`hash_mask = 32767`、`hash_shift = 5`。更新为：

```text
h := ((h << hash_shift) XOR next_byte) AND hash_mask
```

从零开始，十进制字节 A=65、B=66、C=67 依次得到哈希状态 65、2146、3075。再加入 D=68，得到 36，恰好等于重新从零对 B、C、D 计算的结果。三次移位会把更早的贡献推出 15 位掩码。因此，递推能够从一个连续三字节串前进到下一个，而不必重算整个键。

`head[hash]` 保存这个桶最近插入的位置，`prev[position & (W-1)]` 保存其前驱。插入位置 p 时，宏先把旧桶头写入 p 的前驱槽位，并把它作为 `match_head` 返回，然后才把 p 发布为新桶头。搜索从**旧**桶头开始，所以插入当前位置不会立即产生一个与自身匹配的候选。

这不是“先搜索自己再排除自己”。固定版本的普通 [`INSERT_STRING` 宏，160–163 行](https://github.com/madler/zlib/blob/757f0527154291bcf6bfbd6396ecde6bedd2db95/deflate.c#L160-L163)保留了操作顺序：

```c
#define INSERT_STRING(s, str, match_head) \
   (UPDATE_HASH(s, s->ins_h, s->window[(str) + (MIN_MATCH-1)]), \
    match_head = s->prev[(str) & s->w_mask] = s->head[s->ins_h], \
    s->head[s->ins_h] = (Pos)(str))
```

第一行命名宏及三个参数。第二行用当前位置的第三字节完成哈希更新。第三行把旧桶头同时存入前驱槽位和返回变量 `match_head`。第四行才把当前位置发布为新桶头。逗号表达式按这个次序执行；`FASTEST` 配置另有不维护前驱链的分支，不能套用这段代码的全部论证。

前驱数组只有 W 个槽位，p 与 p+W 会复用同一槽位。这节省了内存，但只有当 p 仍属于相应保留代际时，这个槽位才能解释成 p 当时记录的前驱。滑动 W 会保留 `p mod W`，因此保留链接可以继续使用原来的槽位，只改变其中保存的位置值。零表示 `NIL`，实际源码不会把位置零作为普通候选提供给搜索。

哈希只是过滤器，不是内容相等的证明。下一篇进入[候选搜索与延迟决策](/sample/match-search.html)，观察一条引用成为符号前经过哪些检查。完整 C 执行与公开调用的连接仍需证明确认（**to confirm**）；[压缩实现论证](/reference/docs/proof/deflate.html#d-window-bounds-and-fill_window)记录对应的精确义务。
